1. Apa Itu Open/Closed Principle?

"Class harus terbuka untuk ekstensi, tapi tertutup untuk modifikasi."

— Bertrand Meyer, dipopulerkan oleh Robert C. Martin

OCP adalah prinsip kedua dari SOLID. Intinya: saat menambah fitur baru, kita cukup membuat class baru (ekstensi), tanpa mengubah class lama yang sudah berjalan (modifikasi).

Dua Kata Kunci
  • Terbuka untuk ekstensi — kita boleh menambah perilaku baru (biasanya lewat class baru).
  • Tertutup untuk modifikasi — kita tidak boleh mengedit class yang sudah jadi dan teruji.

Analogi singkat: sebuah stop kontak listrik. Anda bisa mencolok TV, kipas, charger HP, laptop — tanpa membongkar stop kontaknya. Stop kontak itu terbuka untuk alat baru, tapi tertutup untuk modifikasi.

2. Memahami Masalah: Kasus DiscountCalculator

Perhatikan kode berikut — ini contoh kode yang SALAH karena melanggar OCP.

❌ SALAH — Melanggar OCP 
<?php

class DiscountCalculator
{
    public function calculate(string $customerType, float $price): float
    {
        if ($customerType === 'regular') {
            return $price;
        }
        if ($customerType === 'member') {
            return $price * 0.9;
        }
        if ($customerType === 'vip') {
            return $price * 0.8;
        }
        // ← di sini nanti nambah terus
        return $price;
    }
}

Pertanyaan: Kalau ada tipe customer baru, apa yang harus dilakukan?

Jawaban: Buka file DiscountCalculator.php dan edit. Inilah pelanggaran OCP. Setiap fitur baru = modifikasi class lama.

3. Skenario Nyata: Satu per Satu

Bayangkan Anda sudah rilis ke production. Sekarang atasan minta tambahan bertahap. Mari kita lihat apa yang terjadi.

📅 Bulan 1 — Rilis awal

if ($customerType === 'regular') { ... }
if ($customerType === 'member')  { ... }
if ($customerType === 'vip')     { ... }

✅ Berjalan. File DiscountCalculator.php aman.

📅 Bulan 2 — Marketing minta tipe "mahasiswa" diskon 15%

Anda buka lagi file DiscountCalculator.php:

if ($customerType === 'mahasiswa') {
    return $price * 0.85;
}

⚠️ File yang tadinya sudah dites dan berjalan, sekarang diubah. Anda harus tes ulang seluruh method — jangan-jangan if baru mengganggu logika vip.

📅 Bulan 3 — Ada program "lansia" diskon 20%

if ($customerType === 'lansia') {
    return $price * 0.80;
}

⚠️ Edit lagi. Tes ulang lagi.

📅 Bulan 4 — Ada "member premium" diskon 25%

if ($customerType === 'premium') {
    return $price * 0.75;
}

⚠️ Edit lagi. File ini sekarang jadi 4x lebih panjang dari awal.

📅 Bulan 5 — Ada "reseller" 30%, "karyawan" 40%, "partner" 35%...

Terus begini. File yang tadinya 10 baris, sekarang 80 baris if. Dan setiap kali edit, risiko merusak yang lain makin besar.

4. Kenapa Melanggar OCP Itu Bermasalah?

MasalahPenjelasan
File terus dibongkar Setiap fitur baru = edit file lama. Padahal file itu seharusnya "sudah selesai".
Risiko bug lama muncul Mengubah if bisa tidak sengaja merusak if yang sudah berjalan.
Tes ulang berkali-kali Setiap edit = harus tes SEMUA tipe customer lagi.
Konflik tim Kalau 2 developer edit file yang sama bersamaan → konflik Git.
Sulit dilacak "Kapan tipe X ditambahkan?" harus lihat history commit panjang.
Melanggar OCP Karena class ini tidak tertutup dari modifikasi.
"Melanggar OCP" Maksudnya Apa? Ingat definisi OCP:

✅ Terbuka untuk ekstensi (nambah fitur) — boleh
❌ Tertutup untuk modifikasi (edit kode lama) — seharusnya tidak boleh

Kode DiscountCalculator di atas melanggar karena:
  • Nambah tipe customer = modifikasi (buka & edit file lama) ❌
  • Seharusnya nambah tipe customer = ekstensi (buat file baru) ✅

5. Versi BENAR dengan OCP

Bandingkan dengan versi yang menerapkan OCP:

INTERFACE — Kontrak 
<?php
// src/Discounts/DiscountStrategy.php
namespace App\Discounts;

interface DiscountStrategy
{
    public function apply(float $price): float;
}
✅ Implementasi Spesifik 
<?php
// src/Discounts/VipDiscount.php
namespace App\Discounts;

class VipDiscount implements DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price * 0.8;
    }
}

Sekarang, bayangkan atasan minta tipe "mahasiswa" diskon 15%. Apa yang Anda lakukan?

✅ File BARU — Tanpa Sentuh yang Lama 
<?php
// src/Discounts/StudentDiscount.php
namespace App\Discounts;

class StudentDiscount implements DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price * 0.85;
    }
}
Selesai. Anda tidak menyentuh DiscountCalculator.php, VipDiscount.php, atau file apa pun yang sudah berjalan. Nol risiko merusak kode lama.

5.1 Ilustrasi Perbedaan

❌ TANPA OCP — "1 class, tambah terus" DiscountCalculator.php ├── if regular ├── if member ├── if vip ├── if mahasiswa ← EDIT di sini ├── if lansia ← EDIT di sini ├── if premium ← EDIT di sini └── if reseller ← EDIT di sini Setiap fitur baru = bongkar file lama.
✅ DENGAN OCP — "banyak class kecil, tinggal tambah file" DiscountCalculator.php (tidak pernah diubah lagi) ├── RegularDiscount.php ├── MemberDiscount.php ├── VipDiscount.php ├── StudentDiscount.php ← FILE BARU ├── SeniorDiscount.php ← FILE BARU ├── PremiumDiscount.php ← FILE BARU └── ResellerDiscount.php ← FILE BARU Setiap fitur baru = buat file baru, tidak sentuh yang lama.

6. 3 Cara Menerapkan OCP di PHP

Banyak yang bertanya: "Apakah OCP harus pakai interface?" Jawabannya: tidak harus — tapi interface adalah cara paling umum dan paling rapi. Ada 3 cara utama.

Cara 1 — Interface (Paling Umum & Direkomendasikan)

INTERFACE 
<?php
// src/Discounts/DiscountStrategy.php
namespace App\Discounts;

interface DiscountStrategy
{
    public function apply(float $price): float;
}
✅ Implementasi 1 
<?php
namespace App\Discounts;

class VipDiscount implements DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price * 0.8;
    }
}
✅ Implementasi 2 
<?php
namespace App\Discounts;

class StudentDiscount implements DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price * 0.85;
    }
}
Kekurangan
  • Tidak bisa berisi implementasi default
  • Semua method harus ditulis ulang di setiap class
Kelebihan
  • Kontrak jelas — semua implementor wajib punya apply()
  • Bisa multi-implement (implements A, B, C)
  • Fleksibel — class tidak terikat hirarki inheritance

Kapan dipakai: saat Anda hanya butuh kontrak perilaku tanpa logic bersama.

Cara 2 — Abstract Class

ABSTRACT CLASS 
<?php
namespace App\Discounts;

abstract class DiscountStrategy
{
    abstract public function apply(float $price): float;

    // Method konkret yang bisa dipakai semua turunan
    public function formatRupiah(float $amount): string
    {
        return "Rp " . number_format($amount, 0, ',', '.');
    }
}
✅ Turunan 1 
<?php
namespace App\Discounts;

class VipDiscount extends DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price * 0.8;
    }
}
✅ Turunan 2 
<?php
namespace App\Discounts;

class StudentDiscount extends DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price * 0.85;
    }
}
Kekurangan
  • Hanya bisa extends satu abstract class (PHP single inheritance)
  • Lebih terikat hirarki
Kelebihan
  • Bisa berisi logic bersama (misal formatRupiah())
  • Bisa berisi property
  • Kontrak tetap jelas lewat abstract

Kapan dipakai: saat ada logic bersama yang ingin dipakai ulang oleh semua turunan.

Cara 3 — Tanpa Interface Sama Sekali (Duck Typing)

⚠️ Hati-hati 
<?php
namespace App\Discounts;

class VipDiscount
{
    public function apply(float $price): float
    {
        return $price * 0.8;
    }
}

class StudentDiscount
{
    public function apply(float $price): float
    {
        return $price * 0.85;
    }
}
⚠️ Calculator tanpa type-hint 
<?php
namespace App\Services;

class DiscountCalculator
{
    public function calculate($strategy, float $price): float
    {
        // Tidak ada type-hint interface
        return $strategy->apply($price);
    }
}
Kekurangan
  • Tidak ada kontrak — kalau StudentDiscount lupa punya apply(), baru error saat runtime
  • IDE tidak bisa autocomplete
  • Rawan typo dan bug
  • Tidak bisa di-type-hint dengan aman
Kelebihan
  • Paling ringan, tidak ada file tambahan
  • Cepat untuk project kecil

Kapan dipakai: jarang di project serius. Hanya untuk prototyping atau project super kecil.

7. Perbandingan: Interface vs Abstract vs Tanpa Kontrak

Aspek Interface Abstract Class Tanpa Kontrak
Kontrak perilaku ✅ Kuat ✅ Kuat ❌ Tidak ada
Logic bersama ❌ ✅ Bisa ❌
Property ❌ ✅ Bisa ✅ (tapi bebas)
Multi-inherit ✅ (implements banyak) ❌ (hanya 1) ✅
Type safety ✅ Tinggi ✅ Tinggi ❌ Rendah
IDE autocomplete ✅ ✅ ❌
Cocok untuk Kontrak murni Kontrak + logic bersama Prototyping

8. Kapan Pakai Apa?

Gunakan Interface saat:

  • Anda hanya butuh kontrak perilaku (method apa yang wajib ada).
  • Ingin class bisa mengimplementasikan beberapa kontrak sekaligus.
  • Tidak ada logic bersama yang perlu diwarisi.
  • Ini kasus paling umum — 80% kebutuhan OCP.

Contoh: DiscountStrategy, DatabaseInterface, NotificationChannel, PaymentGateway.

Gunakan Abstract Class saat:

  • Ada logic bersama yang ingin dipakai ulang oleh semua turunan.
  • Ada property yang ingin diwarisi.
  • Anda yakin hirarki ini cukup satu tingkat (tidak perlu multi-inherit).

Contoh: AbstractController (dengan render() bersama), AbstractModel (dengan save() bersama), AbstractReport.

Tanpa kontrak — hampir tidak pernah untuk OCP serius:

  • Hanya untuk eksperimen / prototyping.
  • Untuk production, hampir selalu pakai interface atau abstract class.

9. Kombinasi Terbaik: Interface + Abstract Class

Sering di project nyata, kita kombinasikan keduanya. Ini pola yang dipakai Laravel, Symfony, dan framework besar lainnya.

1. Interface — Kontrak Murni 
<?php
// src/Discounts/DiscountStrategy.php
namespace App\Discounts;

interface DiscountStrategy
{
    public function apply(float $price): float;
    public function getName(): string;
}
2. Abstract Class — Implementasi Sebagian 
<?php
// src/Discounts/BaseDiscount.php
namespace App\Discounts;

abstract class BaseDiscount implements DiscountStrategy
{
    // Implementasi getName() cukup sekali di sini
    public function getName(): string
    {
        return static::class;  // otomatis ambil nama class
    }

    // Method konkret untuk format tampilan
    public function describe(float $price): string
    {
        return $this->getName() . " → " . $this->apply($price);
    }
}
3. Class Konkret — Tinggal Implement yang Belum Ada 
<?php
// src/Discounts/VipDiscount.php
namespace App\Discounts;

class VipDiscount extends BaseDiscount
{
    public function apply(float $price): float
    {
        return $price * 0.8;
    }
}
4. Class Konkret Lain 
<?php
// src/Discounts/StudentDiscount.php
namespace App\Discounts;

class StudentDiscount extends BaseDiscount
{
    public function apply(float $price): float
    {
        return $price * 0.85;
    }
}
Kenapa Ini Bagus?
  • Interface DiscountStrategy = kontrak resmi (bisa di-type-hint).
  • Abstract class BaseDiscount = implementasi umum (tidak duplikasi kode).
  • Class konkret = implementasi spesifik.

Cara pakai di index.php:

index.php 
<?php
require_once __DIR__ . '/vendor/autoload.php';

use App\Discounts\VipDiscount;
use App\Discounts\StudentDiscount;
use App\Services\DiscountCalculator;

$calculator = new DiscountCalculator();

echo $calculator->calculate(new VipDiscount(), 1000000) . PHP_EOL;
echo $calculator->calculate(new StudentDiscount(), 1000000) . PHP_EOL;

// Tambah tipe baru? Cukup buat class baru:
// class SeniorDiscount extends BaseDiscount { ... }
// TANPA edit DiscountCalculator

10. Analogi: Pisau Lipat vs Peralatan Dapur

🔪 Analogi Pisau Lipat Serbaguna

Bayangkan pisau lipat serbaguna:

  • Mau buka kaleng? Buka pisau lipat, cari mata pisau kaleng.
  • Mau potong roti? Buka lagi, tukar mata pisau.
  • Mau buka botol? Buka lagi, tukar lagi.
  • Setiap "fitur baru" = bongkar alat lama.

🍴 Bandingkan dengan Peralatan Dapur Terpisah

  • Butuh buka kaleng? Ambil pembuka kaleng.
  • Butuh potong roti? Ambil pisau roti.
  • Butuh buka botol? Ambil pembuka botol.
  • Setiap "fitur baru" = ambil alat baru. Alat lama tidak disentuh.

Itulah bedanya melanggar OCP vs menerapkan OCP.

🔌 Analogi Stop Kontak Listrik

OCP itu seperti "stop kontak listrik" di rumah.

  • Interface = standar colokan (bentuk, jumlah pin, tegangan). Selama alat elektronik mengikuti standar ini, apapun bisa dicolok.
  • Abstract class = colokan dengan adaptor bawaan — sudah punya kabel, tinggal sambung.
  • Tanpa kontrak = colok alat pakai selotip — mungkin nyala, tapi rawan kebakaran.

OCP tercapai selama Anda menambahkan "alat baru" tanpa membongkar "stop kontak" yang sudah terpasang.

11. Ringkasan Jawaban

11.1 Tentang "Melanggar OCP"

"Melanggar OCP" = setiap kali tambah fitur, Anda terpaksa buka dan edit class lama. Kode lama jadi terus berubah, rawan bug, dan sulit dites.

"Menerapkan OCP" = setiap kali tambah fitur, Anda cukup buat class/file baru. Class lama tetap utuh, sudah teruji, tidak tersentuh.

11.2 Tentang "Apakah Harus Pakai Interface?"

PertanyaanJawaban
Harus pakai interface untuk OCP? ❌ Tidak harus
Interface satu-satunya cara? ❌ Tidak — ada abstract class, bahkan tanpa kontrak
Cara paling umum & direkomendasikan? ✅ Interface (atau interface + abstract class)
Kapan pakai abstract class? Saat ada logic bersama yang mau diwarisi
Kapan pakai interface? Saat hanya butuh kontrak tanpa logic

11.3 Kesimpulan Satu Kalimat

Kesimpulan Dalam konteks DiscountCalculator: setiap ada tipe customer baru, Anda terpaksa "membedah" class itu lagi — padahal seharusnya class itu "selesai" dan hanya perlu "ditambah" dengan class diskon baru di sebelahnya.

11.4 Konsep Kunci untuk Mahasiswa

  • SOLID itu pedoman, bukan aturan mati — jangan over-engineer project kecil.
  • S = pisahkan tanggung jawab → lebih banyak class, lebih rapi.
  • O = tambah fitur tanpa edit class lama → pakai polimorfisme.
  • L = jangan buat turunan yang "menolak" perilaku induk.
  • I = jangan paksa class implement method yang tidak dipakai.
  • D = pakai interface + Dependency Injection → mudah di-test dan diganti.
  • SOLID menyatukan semua materi sebelumnya: class, inheritance, polimorfisme, namespace, Composer, try-catch, class diagram.

12. Latihan & Tugas

Latihan 1 — Identifikasi Pelanggaran OCP

Perhatikan class berikut, lalu jawab pertanyaan:

<?php
class ShippingCalculator
{
    public function calculate(string $courier, float $weight): float
    {
        if ($courier === 'jne') {
            return $weight * 15000;
        }
        if ($courier === 'jnt') {
            return $weight * 12000;
        }
        if ($courier === 'sicepat') {
            return $weight * 10000;
        }
        return 0;
    }
}
  1. Mengapa class ini melanggar OCP?
  2. Kalau ada kurir baru (misal "anteraja"), apa yang harus Anda lakukan?
  3. Sebutkan minimal 3 masalah yang muncul dari cara ini.

Latihan 2 — Refactor dengan Interface

Refactor ShippingCalculator di atas agar menerapkan OCP. Wajib menyertakan:

  • Interface ShippingStrategy dengan method calculate().
  • Minimal 3 implementasi (JneShipping, JntShipping, SicepatShipping).
  • Class ShippingCalculator yang menerima interface di constructor.
  • File index.php yang mendemonstrasikan penggunaan.

Target: menambah kurir baru cukup dengan 1 file baru, tanpa edit class lama.

Latihan 3 — Bandingkan 3 Cara

Buat implementasi yang sama menggunakan 3 pendekatan berbeda:

  1. Interface
  2. Abstract Class
  3. Tanpa kontrak (duck typing)

Untuk setiap pendekatan, tulis:

  • Kelebihan dan kekurangan yang Anda rasakan saat menulis.
  • Bagaimana IDE Anda membantu (atau tidak) di masing-masing.
  • Kesimpulan: mana yang akan Anda pilih untuk production, dan mengapa?

Latihan 4 — Kombinasi Interface + Abstract

Buat sistem notifikasi dengan pola interface + abstract class:

  • Interface NotificationChannel dengan method send(string $to, string $message).
  • Abstract class BaseChannel yang implements interface tersebut dan menyediakan method konkret formatMessage().
  • Turunan: EmailChannel, SmsChannel, WhatsAppChannel.
  • Class NotificationService yang menerima NotificationChannel di constructor.

Target: menambah channel baru hanya dengan 1 file turunan baru.

Tugas Akhir — Refactor Project Praktikum

Ambil salah satu project PHP Anda yang punya if-else atau switch panjang (lebih dari 3 kondisi). Lakukan audit OCP:

  1. Identifikasi bagian mana yang melanggar OCP.
  2. Refactor menggunakan interface (atau abstract class).
  3. Tunjukkan bukti bahwa menambah tipe baru tidak perlu mengedit class lama.
  4. Buat tabel perbandingan sebelum vs sesudah.
  5. Gambar class diagram sebelum dan sesudah.
