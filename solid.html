1. Apa Itu Prinsip SOLID?

SOLID adalah akronim dari 5 prinsip desain dalam pemrograman berorientasi objek (OOP) yang diperkenalkan oleh Robert C. Martin (Uncle Bob) dan dipopulerkan oleh Michael Feathers.

Prinsip-prinsip ini bukan aturan bahasa pemrograman, tapi pedoman cara berpikir ketika merancang class. Tujuannya sederhana: membuat kode yang mudah dibaca, diubah, diuji, dan dikembangkan tanpa harus merusak bagian lain yang sudah berjalan.

Analogi Sehari-hari Bayangkan sebuah pisau lipat serbaguna. Serbaguna, tapi saat satu bagian rusak, susah diperbaiki. Bandingkan dengan peralatan dapur terpisah: pisau khusus potong, talenan khusus, sendok khusus. Kalau pisau tumpul, cukup ganti pisaunya — yang lain aman.

SOLID mengajarkan cara "memisahkan alat" dalam bentuk class.

2. Kenapa Perlu SOLID?

Kode tanpa SOLID cenderung "rapuh". Gejala-gejalanya:

  • Rigid — satu perubahan kecil memaksa banyak file lain diubah.
  • Fragile — mengubah satu bagian, tiba-tiba bagian lain error.
  • Immobile — bagian kode tidak bisa dipakai ulang di project lain.
  • Viscous — solusi cepat (asal jalan) lebih dipilih daripada solusi bersih.

SOLID hadir untuk melawan gejala tersebut. Setelah Anda menguasai SOLID:

AspekSebelum SOLIDSesudah SOLID
Menambah fitur Edit class lama yang sudah panjang Tambah class baru, class lama tetap
Testing Sulit — harus jalankan seluruh aplikasi Mudah — setiap class diuji terpisah
Bug Sulit dilacak — banyak class saling terkait Cepat — jelas tanggung jawab tiap class
Refactor Berisiko tinggi Aman — perubahan terisolasi
Catatan Realistis SOLID bukan aturan mati. Untuk project kecil (1–3 class), menerapkan semua prinsip justru bisa over-engineering. Gunakan SOLID saat aplikasi mulai tumbuh — misalnya saat satu class melebihi 200 baris atau sulit diuji.

3. S — Single Responsibility Principle

S Single Responsibility Principle

"Setiap class hanya boleh punya satu alasan untuk berubah."

Artinya: satu class hanya boleh mengurus satu tanggung jawab. Kalau class Anda punya 3 tanggung jawab berbeda, pisahkan menjadi 3 class.

Contoh SALAH — 1 Class, 3 Tanggung Jawab

<?php

namespace App\Services;

use App\Models\User;

class UserService
{
    // 1. Tanggung jawab: validasi
    public function validateEmail(string $email): bool
    {
        return filter_var($email, FILTER_VALIDATE_EMAIL) !== false;
    }

    // 2. Tanggung jawab: membuat object
    public function createUser(string $name, string $email): User
    {
        return new User($name, $email);
    }

    // 3. Tanggung jawab: menyimpan ke database
    public function saveToDatabase(User $user): void
    {
        // kode PDO / MySQL di sini
    }

    // 4. Tanggung jawab: kirim email
    public function sendWelcomeEmail(User $user): void
    {
        mail($user->getEmail(), 'Selamat datang!', '...');
    }
}

Masalah: Kalau cara kirim email berubah (misal pindah ke SMTP), Anda harus mengedit class ini. Kalau skema database berubah, class ini juga berubah. Kalau aturan validasi berubah, class ini juga berubah.
→ 4 alasan untuk berubah = melanggar SRP.

Contoh BENAR — Pisahkan Tanggung Jawab

<?php
// src/Validators/EmailValidator.php
namespace App\Validators;

class EmailValidator
{
    public function isValid(string $email): bool
    {
        return filter_var($email, FILTER_VALIDATE_EMAIL) !== false;
    }
}
<?php
// src/Repositories/UserRepository.php
namespace App\Repositories;

use App\Models\User;

class UserRepository
{
    public function save(User $user): void
    {
        // kode PDO / MySQL
    }
}
<?php
// src/Services/MailService.php
namespace App\Services;

use App\Models\User;

class MailService
{
    public function sendWelcome(User $user): void
    {
        mail($user->getEmail(), 'Selamat datang!', '...');
    }
}
<?php
// src/Services/UserService.php
namespace App\Services;

use App\Models\User;
use App\Validators\EmailValidator;
use App\Repositories\UserRepository;
use App\Services\MailService;
use InvalidArgumentException;

class UserService
{
    public function __construct(
        private EmailValidator   $validator,
        private UserRepository   $repo,
        private MailService      $mailer
    ) {}

    public function createUser(string $name, string $email): User
    {
        if (!$this->validator->isValid($email)) {
            throw new InvalidArgumentException("Email tidak valid");
        }

        $user = new User($name, $email);
        $this->repo->save($user);
        $this->mailer->sendWelcome($user);

        return $user;
    }
}
Hasilnya
  • EmailValidator hanya urus validasi email.
  • UserRepository hanya urus penyimpanan.
  • MailService hanya urus kirim email.
  • UserService jadi koordinator yang merangkai semuanya.

4. O — Open/Closed Principle

O Open/Closed Principle

"Class harus terbuka untuk ekstensi, tapi tertutup untuk modifikasi."

Artinya: saat menambah fitur baru, kita cukup membuat class baru (ekstensi), tanpa mengubah class lama yang sudah berjalan.

Contoh SALAH — Setiap Tambah Fitur, Edit Class Lama

<?php

namespace App\Services;

class DiscountCalculator
{
    public function calculate(string $customerType, float $price): float
    {
        if ($customerType === 'regular') {
            return $price;
        }
        if ($customerType === 'member') {
            return $price * 0.9;
        }
        if ($customerType === 'vip') {
            return $price * 0.8;
        }

        // Setiap tipe baru → edit class ini lagi!
        // Misal tambah "mahasiswa", "lansia" → tambah if lagi

        return $price;
    }
}

Masalah: Setiap kali ada tipe customer baru, Anda harus edit class DiscountCalculator. Ini melanggar OCP.

Contoh BENAR — Gunakan Interface + Polimorfisme

<?php
// src/Discounts/DiscountStrategy.php
namespace App\Discounts;

interface DiscountStrategy
{
    public function apply(float $price): float;
}
<?php
// src/Discounts/RegularDiscount.php
namespace App\Discounts;

class RegularDiscount implements DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price;
    }
}
<?php
// src/Discounts/MemberDiscount.php
namespace App\Discounts;

class MemberDiscount implements DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price * 0.9;
    }
}
<?php
// src/Discounts/VipDiscount.php
namespace App\Discounts;

class VipDiscount implements DiscountStrategy
{
    public function apply(float $price): float
    {
        return $price * 0.8;
    }
}
<?php
// src/Services/DiscountCalculator.php
namespace App\Services;

use App\Discounts\DiscountStrategy;

class DiscountCalculator
{
    public function calculate(DiscountStrategy $strategy, float $price): float
    {
        return $strategy->apply($price);
    }
}
<?php
// index.php — cara pakai
$calculator = new DiscountCalculator();

echo $calculator->calculate(new VipDiscount(), 1000000);

// Tambah tipe baru? Cukup buat class baru:
// class StudentDiscount implements DiscountStrategy { ... }
// TANPA edit DiscountCalculator
Hasilnya Menambah tipe diskon baru = buat file baru. DiscountCalculator tidak perlu disentuh.

5. L — Liskov Substitution Principle

L Liskov Substitution Principle

"Objek turunan harus bisa menggantikan objek induknya tanpa merusak program."

Artinya: kalau class B adalah turunan class A, maka di mana pun A dipakai, B harus bisa dipakai tanpa error atau perilaku aneh.

Contoh SALAH — Burung & Pinguin

<?php

namespace App\Models;

class Bird
{
    public function fly(): string
    {
        return "Terbang tinggi!";
    }
}
<?php
namespace App\Models;

class Penguin extends Bird
{
    public function fly(): string
    {
        throw new \Exception("Pinguin tidak bisa terbang!");
    }
}
<?php
// index.php
function makeItFly(Bird $bird): void
{
    echo $bird->fly();  // error kalau $bird = Penguin
}

makeItFly(new Penguin());  // BOOM! Exception

Masalah: Penguin adalah Bird secara inheritance, tapi tidak bisa menggantikan Bird di fungsi yang mengandalkan method fly(). Ini melanggar LSP.

Contoh BENAR — Pisahkan Kemampuan

<?php
namespace App\Models;

interface Bird
{
    public function eat(): string;
}

interface FlyingBird extends Bird
{
    public function fly(): string;
}
<?php
namespace App\Models;

class Eagle implements FlyingBird
{
    public function eat(): string  { return "Makan daging"; }
    public function fly(): string  { return "Terbang tinggi!"; }
}
<?php
namespace App\Models;

class Penguin implements Bird
{
    public function eat(): string  { return "Makan ikan"; }
    // tidak perlu implement fly()
}
<?php
// index.php
function feed(Bird $bird): void
{
    echo $bird->eat();   // aman untuk semua Bird
}

function makeItFly(FlyingBird $bird): void
{
    echo $bird->fly();   // hanya untuk yang bisa terbang
}

feed(new Penguin());       // OK
makeItFly(new Eagle());    // OK
// makeItFly(new Penguin()); // error compile — memang tidak boleh
Prinsip Praktis Kalau turunan Anda harus meng-override method induk hanya untuk melempar exception atau "mengosongkan" perilaku, itu tanda kuat LSP dilanggar. Solusinya: pecah interface menjadi lebih kecil, atau ubah hirarki inheritance.

6. I — Interface Segregation Principle

I Interface Segregation Principle

"Jangan paksa class mengimplementasikan method yang tidak dipakainya."

Artinya: lebih baik punya banyak interface kecil yang spesifik daripada satu interface besar yang memaksa semua implementor mengisi method kosong.

Contoh SALAH — Interface Terlalu Gemuk

<?php
namespace App\Contracts;

interface Worker
{
    public function work(): string;
    public function eat(): string;
    public function sleep(): string;
}
<?php
namespace App\Models;

class Robot implements Worker
{
    public function work(): string  { return "Bekerja 24 jam"; }
    public function eat(): string   { return ""; }  // ← tidak masuk akal
    public function sleep(): string { return ""; }  // ← tidak masuk akal
}

Masalah: Robot dipaksa mengimplementasikan eat() dan sleep() padahal tidak butuh. Ini melanggar ISP.

Contoh BENAR — Pisahkan Interface

<?php
namespace App\Contracts;

interface Workable
{
    public function work(): string;
}

interface Eatable
{
    public function eat(): string;
}

interface Sleepable
{
    public function sleep(): string;
}
<?php
namespace App\Models;

use App\Contracts\Workable;

class Robot implements Workable
{
    public function work(): string { return "Bekerja 24 jam"; }
}
<?php
namespace App\Models;

use App\Contracts\Workable;
use App\Contracts\Eatable;
use App\Contracts\Sleepable;

class Human implements Workable, Eatable, Sleepable
{
    public function work(): string  { return "Bekerja 8 jam"; }
    public function eat(): string   { return "Makan siang"; }
    public function sleep(): string { return "Tidur 8 jam"; }
}
Hasilnya Robot hanya implement yang relevan. Human implement semua karena memang butuh. Tidak ada method kosong yang dipaksa.

7. D — Dependency Inversion Principle

D Dependency Inversion Principle

"Bergantunglah pada abstraksi (interface), bukan pada implementasi konkret."

Artinya: class tingkat tinggi (Service) tidak boleh bergantung langsung pada class tingkat rendah (MySQL, Email). Keduanya harus bergantung pada interface.

Contoh SALAH — Bergantung pada Implementasi Konkret

<?php
namespace App\Services;

use App\Models\User;

class UserService
{
    private MySQLDatabase $db;   // ← konkret, bukan abstraksi

    public function __construct()
    {
        $this->db = new MySQLDatabase();  // ← hardcode
    }

    public function createUser(string $name, string $email): User
    {
        $user = new User($name, $email);
        $this->db->insert('users', [
            'name'  => $user->getName(),
            'email' => $user->getEmail()
        ]);
        return $user;
    }
}

Masalah: Kalau nanti ingin ganti dari MySQL ke PostgreSQL, atau ingin unit test dengan database palsu (mock), Anda harus edit class UserService. Ini melanggar DIP.

Contoh BENAR — Bergantung pada Interface

<?php
// src/Contracts/DatabaseInterface.php
namespace App\Contracts;

interface DatabaseInterface
{
    public function insert(string $table, array $data): bool;
}
<?php
// src/Database/MySQLDatabase.php
namespace App\Database;

use App\Contracts\DatabaseInterface;

class MySQLDatabase implements DatabaseInterface
{
    public function insert(string $table, array $data): bool
    {
        // kode MySQL
        return true;
    }
}
<?php
// src/Database/InMemoryDatabase.php — untuk testing
namespace App\Database;

use App\Contracts\DatabaseInterface;

class InMemoryDatabase implements DatabaseInterface
{
    private array $rows = [];

    public function insert(string $table, array $data): bool
    {
        $this->rows[$table][] = $data;
        return true;
    }
}
<?php
// src/Services/UserService.php
namespace App\Services;

use App\Models\User;
use App\Contracts\DatabaseInterface;

class UserService
{
    public function __construct(
        private DatabaseInterface $db   // ← interface, bukan class konkret
    ) {}

    public function createUser(string $name, string $email): User
    {
        $user = new User($name, $email);
        $this->db->insert('users', [
            'name'  => $user->getName(),
            'email' => $user->getEmail()
        ]);
        return $user;
    }
}
<?php
// index.php
use App\Services\UserService;
use App\Database\MySQLDatabase;
use App\Database\InMemoryDatabase;

// Produksi
$service = new UserService(new MySQLDatabase());

// Testing (tidak perlu database sungguhan)
$service = new UserService(new InMemoryDatabase());
Teknik Dependency Injection (DI) Perhatikan constructor UserService di atas — ia menerima DatabaseInterface dari luar, bukan membuat sendiri. Inilah Dependency Injection, penerapan paling umum dari DIP.

Framework modern seperti Laravel punya service container yang melakukan DI ini secara otomatis — cukup type-hint di constructor, framework yang menyuntikkan object konkretnya.

8. Kaitan dengan Materi Sebelumnya

SOLID bukan topik terpisah — ia menyatukan semua yang sudah kita pelajari:

Materi SebelumnyaBagaimana Terhubung dengan SOLID
Class & Object SOLID adalah pedoman bagaimana merancang class yang baik.
Encapsulation SRP mendorong setiap class menyembunyikan detailnya sendiri.
Inheritance LSP adalah aturan agar inheritance tidak merusak program.
Polymorphism OCP dan DIP sangat bergantung pada polimorfisme lewat interface.
Namespace & PSR-4 Setiap prinsip SOLID mendorong pemisahan class ke folder yang jelas — praktik langsung PSR-4.
Composer Autoload Semakin banyak class (karena SRP), autoload jadi wajib — tidak mungkin pakai require manual.
Try-Catch & Exception Custom Exception (InvalidEmailException, dll.) adalah bagian dari desain yang bersih — memisahkan alur normal dari alur error.
Class Diagram Class Diagram adalah alat visual untuk memeriksa apakah desain Anda sudah SOLID — misal, lihat apakah ada class dengan 10 method tidak berhubungan (SRP dilanggar).
Urutan Pembelajaran yang Disarankan
1. Class & Object
2. Encapsulation → Inheritance → Polymorphism
3. Namespace & PSR-4
4. Composer Autoload
5. Try-Catch & Exception
6. Class Diagram
7. → SOLID (materi ini)
8. Design Pattern (Strategy, Factory, Repository, dll.)
9. Framework (Laravel / Symfony)

9. Latihan & Tugas

Latihan 1 — Identifikasi Pelanggaran SRP

Perhatikan kode berikut. Identifikasi berapa tanggung jawab yang ada, lalu pecah menjadi class-class terpisah:

<?php
class OrderProcessor
{
    public function validateOrder(array $order): bool { ... }
    public function calculateTotal(array $order): float { ... }
    public function saveToDatabase(array $order): void { ... }
    public function sendEmailConfirmation(array $order): void { ... }
    public function generatePdfInvoice(array $order): string { ... }
}

Petunjuk: Minimal ada 5 tanggung jawab berbeda di sini.

Latihan 2 — Terapkan OCP

Kode berikut melanggar OCP. Refactor agar menambah tipe pembayaran baru cukup dengan membuat class baru:

<?php
class PaymentProcessor
{
    public function process(string $type, float $amount): string
    {
        if ($type === 'credit_card') {
            return "Bayar $amount via kartu kredit";
        }
        if ($type === 'bank_transfer') {
            return "Transfer $amount ke bank";
        }
        if ($type === 'e_wallet') {
            return "Bayar $amount via e-wallet";
        }
        return "Tipe tidak dikenal";
    }
}

Latihan 3 — Perbaiki Pelanggaran LSP

Kode berikut melanggar LSP. Perbaiki hirarki class-nya:

<?php
class Vehicle {
    public function startEngine(): string { return "Mesin menyala"; }
    public function pedal(): string { return "Gas!"; }
}

class Bicycle extends Vehicle {
    public function startEngine(): string {
        throw new \Exception("Sepeda tidak punya mesin!");
    }
}

Petunjuk: Pisahkan kemampuan "bermesin" dan "tidak bermesin".

Latihan 4 — Terapkan DIP dengan Dependency Injection

Refactor kode berikut agar NotificationService bisa dengan mudah diganti dari email ke SMS / WhatsApp:

<?php
class NotificationService
{
    public function send(string $message): void
    {
        mail('user@example.com', 'Notifikasi', $message);
    }
}

Target: Buat interface NotificationChannel, implementasi EmailChannel, SmsChannel, lalu NotificationService menerima salah satunya lewat constructor.
