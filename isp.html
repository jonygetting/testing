1. Apa Itu Interface Segregation Principle?

"Jangan paksa class mengimplementasikan method yang tidak dipakainya."

— Robert C. Martin (Uncle Bob)

ISP adalah prinsip keempat dari SOLID. Intinya: lebih baik punya banyak interface kecil yang spesifik daripada satu interface besar yang memaksa semua implementor mengisi method kosong.

Dengan kata lain: segregate (pisahkan) interface sesuai kebutuhan masing-masing class. Jangan membuat "interface serba bisa" yang akhirnya membebani class dengan method yang tidak relevan.

Analogi Sehari-hari Bayangkan Anda membeli pisau lipat serbaguna dengan 20 mata pisau: buka kaleng, potong roti, buka botol, gunting kuku, obeng, dll.

Anda hanya butuh satu fungsi: membuka botol. Tapi karena pisau lipat itu "serba bisa", Anda terpaksa membawa 20 mata pisau yang tidak Anda butuhkan — berat, ribet, dan membingungkan.

ISP mengajarkan: gunakan alat yang spesifik sesuai kebutuhan. Mau buka botol? Beli pembuka botol saja.

1.1 Definisi Formal (Sederhana)

"Klien tidak boleh dipaksa bergantung pada method yang tidak digunakannya."

Artinya: kalau sebuah class hanya butuh method work(), jangan paksa class itu mengimplementasikan eat() dan sleep() sekaligus. Pecah interface-nya.

2. Kenapa ISP Penting?

AspekTanpa ISPDengan ISP
Kode class Penuh method kosong (dummy) Hanya method yang relevan
Testing Sulit — harus setup method yang tidak dipakai Mudah — fokus pada satu kontrak kecil
Menambah implementor Berisiko — wajib implement semua method Aman — cukup implement yang relevan
Memahami kontrak Sulit — interface besar, tidak jelas tujuannya Mudah — interface kecil dan spesifik
Reuse Rendah — interface gemuk sulit dipakai ulang Tinggi — interface kecil mudah dikombinasi
Type safety Rendah — banyak method tidak relevan Tinggi — type-hint tepat sasaran
Manfaat Utama ISP membuat kode lebih bersih, lebih mudah dites, dan lebih fleksibel. Class tidak lagi "terpaksa" mengimplementasikan method yang tidak dipakai — sehingga setiap class benar-benar fokus pada tanggung jawabnya.

3. Gejala-Gejala Pelanggaran ISP

Kenali tanda-tanda berikut di kode Anda:

  • Banyak method di class implementor yang hanya berisi: return "";, return null;, atau throw new \Exception("tidak didukung");
  • Interface punya lebih dari 5 method dan tidak semua dipakai oleh semua implementor.
  • Nama interface terlalu umum seperti Worker, Manager, Service, atau Handler — biasanya tanda interface gemuk.
  • Ada komentar di class: // method ini tidak dipakai atau // sengaja dikosongkan.
  • Setiap kali menambah method baru ke interface, Anda harus mengedit banyak class yang mengimplementasikannya — padahal method itu tidak relevan untuk sebagian besar class.
  • Class implementor dipaksa mengimplementasikan method yang sebenarnya menjadi tanggung jawab class lain.
Aturan Cepat Kalau Anda menemukan method kosong atau melempar exception di class implementor, itu tanda kuat ISP dilanggar.

Solusinya: pecah interface gemuk menjadi interface kecil yang spesifik sesuai kebutuhan.

4. Kode yang Melanggar ISP (Studi Kasus Worker)

Kita mulai dengan contoh klasik: Worker (Pekerja). Bayangkan kita punya interface Worker yang "serba bisa" — semua pekerja dianggap bisa work(), eat(), dan sleep().

4.1 Interface Gemuk (Salah)

❌ SALAH — Interface Terlalu Gemuk 
<?php
// src/Contracts/Worker.php
namespace App\Contracts;

interface Worker
{
    public function work(): string;
    public function eat(): string;
    public function sleep(): string;
}

4.2 Implementasi yang "Terpaksa"

❌ SALAH — Human Dipaksa Implement Semua 
<?php
// src/Models/Human.php
namespace App\Models;

use App\Contracts\Worker;

class Human implements Worker
{
    public function work(): string
    {
        return "Bekerja 8 jam";
    }

    public function eat(): string
    {
        return "Makan siang";
    }

    public function sleep(): string
    {
        return "Tidur 8 jam";
    }
}
❌ SALAH — Robot Dipaksa Implement yang Tidak Relevan 
<?php
// src/Models/Robot.php
namespace App\Models;

use App\Contracts\Worker;

class Robot implements Worker
{
    public function work(): string
    {
        return "Bekerja 24 jam";
    }

    // ⚠️ Robot tidak makan — tapi dipaksa implement
    public function eat(): string
    {
        return "";  // method kosong
    }

    // ⚠️ Robot tidak tidur — tapi dipaksa implement
    public function sleep(): string
    {
        return "";  // method kosong
    }
}

4.3 Kode Klien yang Rapuh

❌ SALAH — Kode Klien Ragu-Ragu 
<?php
// index.php
require_once __DIR__ . '/vendor/autoload.php';

use App\Contracts\Worker;
use App\Models\Human;
use App\Models\Robot;

function describeWorker(Worker $worker): void
{
    echo $worker->work() . PHP_EOL;

    // ⚠️ Harus cek manual karena tidak semua worker relevan
    if ($worker instanceof Human) {
        echo $worker->eat() . PHP_EOL;
        echo $worker->sleep() . PHP_EOL;
    }

    // Robot? Method eat() dan sleep() ada, tapi kosong — membingungkan!
}

describeWorker(new Human());
describeWorker(new Robot());
Masalah Utama
  • Robot dipaksa punya method eat() dan sleep() yang tidak relevan.
  • Method diisi kosong (return "";) — membingungkan pembaca kode.
  • Kode klien harus melakukan pengecekan instanceof manual.
  • Melanggar ISP: class dipaksa implement method yang tidak dipakainya.

5. Analisis Masalah pada Kode Tersebut

Mari kita bedah: apa yang sebenarnya salah?

NoMasalahPenjelasan
1 Interface terlalu gemuk Worker memaksa 3 method padahal tidak semua pekerja butuh ketiganya.
2 Method kosong di implementor Robot::eat() dan Robot::sleep() diisi kosong — tanda "keterpaksaan".
3 Kode klien ragu Klien harus cek instanceof Human untuk memastikan method aman dipanggil.
4 Sulit menambah implementor baru Setiap worker baru wajib implement eat() dan sleep() — meski tidak butuh.
5 Melanggar ISP Class dipaksa bergantung pada method yang tidak dipakainya.

5.1 Dampak Nyata Pelanggaran Ini

  • Kode penuh "dummy method" — membingungkan pembaca dan menyulitkan maintenance.
  • Menambah implementor baru selalu berat — setiap class baru wajib implement semua method interface, meskipun separuhnya kosong.
  • Kode klien penuh intaian — instanceof atau get_class() di mana-mana.
  • Kontrak interface tidak jelas — pembaca tidak tahu method mana yang benar-benar didukung oleh implementor tertentu.
  • Melanggar prinsip "interface = janji" — kalau implementor mengosongkan method, berarti janji itu dilanggar.

6. Refactor: Menerapkan ISP

Solusinya: pecah interface Worker menjadi interface kecil yang spesifik — Workable, Eatable, Sleepable. Setiap class hanya mengimplementasikan interface yang relevan untuk dirinya.

1

Interface Workable — Kontrak Bekerja

Hanya berisi method work(). Semua pekerja (baik manusia maupun robot) bisa implement ini.

INTERFACE 
<?php
// src/Contracts/Workable.php
namespace App\Contracts;

interface Workable
{
    public function work(): string;
}
2

Interface Eatable — Kontrak Makan

Hanya berisi method eat(). Hanya makhluk hidup yang mengimplementasi ini.

INTERFACE 
<?php
// src/Contracts/Eatable.php
namespace App\Contracts;

interface Eatable
{
    public function eat(): string;
}
3

Interface Sleepable — Kontrak Tidur

Hanya berisi method sleep(). Hanya makhluk hidup yang butuh tidur.

INTERFACE 
<?php
// src/Contracts/Sleepable.php
namespace App\Contracts;

interface Sleepable
{
    public function sleep(): string;
}
4

Class Robot — Hanya Implement yang Relevan

Robot hanya mengimplementasikan Workable — karena robot memang hanya bekerja, tidak makan, tidak tidur. Tidak ada method kosong!

✅ ISP Terpenuhi 
<?php
// src/Models/Robot.php
namespace App\Models;

use App\Contracts\Workable;

class Robot implements Workable
{
    public function work(): string
    {
        return "Bekerja 24 jam";
    }

    // Tidak implement eat() — karena robot tidak makan
    // Tidak implement sleep() — karena robot tidak tidur
}
5

Class Human — Implement Semua yang Relevan

Manusia mengimplementasikan ketiganya — karena manusia memang bekerja, makan, dan tidur.

✅ ISP Terpenuhi 
<?php
// src/Models/Human.php
namespace App\Models;

use App\Contracts\Workable;
use App\Contracts\Eatable;
use App\Contracts\Sleepable;

class Human implements Workable, Eatable, Sleepable
{
    public function work(): string
    {
        return "Bekerja 8 jam";
    }

    public function eat(): string
    {
        return "Makan siang";
    }

    public function sleep(): string
    {
        return "Tidur 8 jam";
    }
}
6

Class Android — Contoh Implementor Baru

Android adalah robot humanoid — bisa bekerja, dan bisa "mengisi daya" (dianalogikan seperti makan). Tapi tetap tidak tidur.

✅ ISP Terpenuhi 
<?php
// src/Models/Android.php
namespace App\Models;

use App\Contracts\Workable;
use App\Contracts\Eatable;

class Android implements Workable, Eatable
{
    public function work(): string
    {
        return "Bekerja 20 jam";
    }

    public function eat(): string
    {
        return "Mengisi daya listrik";
    }

    // Tidak implement sleep() — karena android tidak tidur
}
7

Kode Klien — Sekarang Aman dan Type-Safe

Klien bisa meminta kontrak yang spesifik sesuai kebutuhannya. Tidak perlu cek instanceof lagi.

index.php 
<?php
require_once __DIR__ . '/vendor/autoload.php';

use App\Contracts\Workable;
use App\Contracts\Eatable;
use App\Contracts\Sleepable;
use App\Models\Human;
use App\Models\Robot;
use App\Models\Android;

// Fungsi yang hanya butuh "bekerja"
function assignWork(Workable $worker): void
{
    echo $worker->work() . PHP_EOL;
}

// Fungsi yang hanya butuh "makan"
function feed(Eatable $eater): void
{
    echo $eater->eat() . PHP_EOL;
}

// Fungsi yang hanya butuh "tidur"
function rest(Sleepable $sleeper): void
{
    echo $sleeper->sleep() . PHP_EOL;
}

// ==================== PENGGUNAAN ====================

// Semua bisa bekerja
assignWork(new Human());    // Bekerja 8 jam
assignWork(new Robot());    // Bekerja 24 jam
assignWork(new Android());  // Bekerja 20 jam

// Hanya yang bisa makan
feed(new Human());          // Makan siang
feed(new Android());        // Mengisi daya listrik
// feed(new Robot());       // ❌ ERROR COMPILE — Robot tidak Eatable

// Hanya yang bisa tidur
rest(new Human());          // Tidur 8 jam
// rest(new Robot());       // ❌ ERROR COMPILE — Robot tidak Sleepable
// rest(new Android());     // ❌ ERROR COMPILE — Android tidak Sleepable
Hasil Refactor Sekarang:
  • Robot hanya implement Workable — tidak ada method kosong.
  • Human implement ketiganya — karena memang relevan.
  • Android implement Workable + Eatable — kombinasi baru tanpa ubah interface.
  • Klien bisa meminta kontrak spesifik — error terdeteksi saat compile, bukan runtime.
  • Tambah implementor baru = cukup pilih interface yang relevan.

7. Penggunaan Class, Interface, Abstract, dan Polimorfisme

Refactor ISP di atas memanfaatkan konsep OOP secara tepat. Berikut ringkasan penggunaan masing-masing konsep:

CLASS
Class Biasa

Human, Robot, Android — masing-masing adalah class konkret yang bisa langsung diinstansiasi dengan new.

Setiap class hanya mengimplementasi interface yang relevan untuk dirinya.

INTERFACE
Interface (Kecil & Spesifik)

Workable, Eatable, Sleepable — masing-masing hanya berisi satu method.

Inilah inti ISP: interface kecil lebih baik daripada interface gemuk.

ABSTRACT CLASS
Abstract Class

Pada contoh ini tidak digunakan karena tidak ada logic bersama yang perlu diwarisi. Interface sudah cukup.

(Akan dibahas di bagian 7.1 kapan abstract class tepat dipakai dalam konteks ISP.)

POLIMORFISME
Polimorfisme

assignWork(Workable $worker) bisa menerima Human, Robot, atau Android — semua berperilaku sesuai kontrak work().

Inilah polimorfisme yang bersih karena ISP terpenuhi.

7.1 Kapan Pakai Apa? (pada konteks ISP ini)

KebutuhanGunakanContoh di Modul Ini
Kontrak tunggal yang spesifik Interface kecil Workable, Eatable, Sleepable
Class konkret dengan kombinasi kontrak Class + multiple implements Human implements Workable, Eatable, Sleepable
Ada logic bersama + kontrak Abstract class Lihat contoh di bawah (7.2)
Memperlakukan implementor secara seragam Polimorfisme assignWork(Workable $worker)

7.2 Kapan Abstract Class Dipakai dalam Konteks ISP?

Abstract class juga bisa dipakai bersama ISP, asalkan tetap memisahkan interface yang tidak relevan. Contoh: kita ingin semua pekerja punya method getName() dengan format yang konsisten — sekaligus tetap memisahkan kemampuan eat() dan sleep().

ABSTRACT CLASS — Logic Bersama untuk Pekerja 
<?php
// src/Abstracts/AbstractWorker.php
namespace App\Abstracts;

use App\Contracts\Workable;

abstract class AbstractWorker implements Workable
{
    public function __construct(protected string $name) {}

    // Method konkret — bisa dipakai semua turunan
    public function getName(): string
    {
        return $this->name;
    }

    // Method abstrak — WAJIB diimplementasi turunan
    abstract public function work(): string;
}
INTERFACE TETAP TERPISAH 
<?php
// src/Contracts/Eatable.php
namespace App\Contracts;

interface Eatable
{
    public function eat(): string;
}

// src/Contracts/Sleepable.php
namespace App\Contracts;

interface Sleepable
{
    public function sleep(): string;
}
✅ Turunan — Kombinasi Interface Sesuai Kebutuhan 
<?php
// src/Models/Human.php
namespace App\Models;

use App\Abstracts\AbstractWorker;
use App\Contracts\Eatable;
use App\Contracts\Sleepable;

class Human extends AbstractWorker implements Eatable, Sleepable
{
    public function work(): string
    {
        return $this->getName() . " bekerja 8 jam";
    }

    public function eat(): string
    {
        return $this->getName() . " makan siang";
    }

    public function sleep(): string
    {
        return $this->getName() . " tidur 8 jam";
    }
}
✅ Turunan — Hanya yang Relevan 
<?php
// src/Models/Robot.php
namespace App\Models;

use App\Abstracts\AbstractWorker;

class Robot extends AbstractWorker
{
    public function work(): string
    {
        return $this->getName() . " bekerja 24 jam";
    }

    // Tidak implement Eatable, tidak implement Sleepable
}

Kode klien:

<?php
use App\Contracts\Workable;
use App\Contracts\Eatable;
use App\Contracts\Sleepable;
use App\Models\Human;
use App\Models\Robot;

function assignWork(Workable $worker): void
{
    echo $worker->work() . PHP_EOL;
}

function feed(Eatable $eater): void
{
    echo $eater->eat() . PHP_EOL;
}

function rest(Sleepable $sleeper): void
{
    echo $sleeper->sleep() . PHP_EOL;
}

assignWork(new Human('Budi'));   // Budi bekerja 8 jam
assignWork(new Robot('R2D2'));   // R2D2 bekerja 24 jam
feed(new Human('Budi'));         // Budi makan siang
// feed(new Robot('R2D2'));      // ❌ ERROR COMPILE — Robot tidak Eatable
Pola Kombinasi Interface Kecil + Abstract Class
  • Interface Workable, Eatable, Sleepable — kontrak kecil dan spesifik.
  • Abstract class AbstractWorker — implementasi umum (logic bersama, property name).
  • Class konkret — pilih kombinasi interface yang relevan.
Inilah pola yang paling umum dipakai di framework modern (Laravel, Symfony) dan sangat konsisten dengan ISP.

8. Perbandingan Sebelum vs Sesudah

❌ SEBELUM (Melanggar ISP)
  • Satu interface Worker dengan 3 method
  • Robot::eat() dan Robot::sleep() kosong
  • Kode klien penuh instanceof manual
  • Setiap implementor wajib implement semua method
  • Interface tidak jelas tujuannya
  • Tambah implementor baru = berat
✅ SESUDAH (ISP Terpenuhi)
  • Tiga interface kecil: Workable, Eatable, Sleepable
  • Robot hanya implement Workable
  • Kode klien type-safe, tanpa instanceof
  • Setiap implementor pilih interface yang relevan
  • Interface kecil dan jelas tujuannya
  • Tambah implementor baru = ringan
Aspek❌ Sebelum ISP✅ Sesudah ISP
Jumlah interface 1 (Worker dengan 3 method) 3 (Workable, Eatable, Sleepable)
Method di Robot 3 (2 kosong) 1 (work())
Kode klien Penuh instanceof Type-safe, tanpa cek manual
Kontrak interface Kabur Jelas dan spesifik
Menambah implementor Berat (semua method wajib) Ringan (pilih yang relevan)
Kombinasi baru Tidak mungkin Mudah (Android implements Workable, Eatable)

9. Aturan Praktis ISP

Berikut aturan praktis yang bisa Anda hafal untuk menghindari pelanggaran ISP:

AturanPenjelasan
Interface kecil > interface gemuk Lebih baik banyak interface kecil (1–3 method) daripada satu interface besar (10+ method).
Interface = janji Kalau class mengimplementasi interface, berarti dia berjanji bisa memenuhi semua method-nya dengan benar.
Jangan kosongkan method Kalau turunan mengosongkan method, berarti dia tidak bisa memenuhi janji interface — pecah interface-nya.
Pisahkan berdasarkan peran Bukan berdasarkan tipe class. Contoh: Eatable untuk semua yang bisa makan, bukan Human atau Animal.
Kombinasikan interface Class boleh implement banyak interface kecil sekaligus: class Human implements Workable, Eatable, Sleepable.
Interface = klien yang menentukan Interface harus dibuat dari kebutuhan klien, bukan dari keinginan implementor.
Aturan Emas Saat membuat interface, tanyakan:

"Apakah semua class yang akan mengimplementasi interface ini benar-benar butuh semua method-nya?"

Kalau tidak, berarti interface itu perlu dipecah. ISP dilanggar.

11. Kaitan dengan Prinsip SOLID Lain

ISP tidak berdiri sendiri — ia sangat erat kaitannya dengan prinsip SOLID lainnya:

PrinsipKaitan dengan ISP
S — Single Responsibility Interface kecil biasanya juga mengikuti SRP: satu interface = satu tanggung jawab.
O — Open/Closed ISP memudahkan OCP: menambah implementor baru cukup pilih interface yang relevan, tanpa ubah interface lama.
L — Liskov Substitution ISP mencegah pelanggaran LSP: kalau interface dipecah, tidak ada turunan yang "menolak" method induk.
D — Dependency Inversion ISP memudahkan DIP: klien bergantung pada interface kecil yang spesifik, bukan interface gemuk yang berisi banyak method tidak relevan.
ISP dan LSP — Pasangan Serasi LSP dan ISP sering disebut "saudara kembar" karena keduanya berkutat pada kontrak interface:
  • LSP — memastikan turunan bisa memenuhi kontrak induk.
  • ISP — memastikan kontrak tidak membebani implementor dengan method yang tidak dipakai.
Kalau LSP dilanggar (turunan melempar exception), biasanya solusinya adalah memecah interface — dan itulah ISP.

12. Latihan & Tugas

Latihan 1 — Identifikasi Pelanggaran ISP

Perhatikan interface berikut, lalu jawab pertanyaan:

<?php
interface MultiFunctionDevice
{
    public function printDocument(string $doc): string;
    public function scanDocument(string $doc): string;
    public function faxDocument(string $doc): string;
    public function copyDocument(string $doc): string;
}

class SimplePrinter implements MultiFunctionDevice
{
    public function printDocument(string $doc): string { return "Print: $doc"; }
    public function scanDocument(string $doc): string  { return ""; }
    public function faxDocument(string $doc): string   { return ""; }
    public function copyDocument(string $doc): string  { return ""; }
}
  1. Mengapa SimplePrinter melanggar ISP?
  2. Berapa method yang diimplementasi tapi tidak dipakai?
  3. Apa dampak bagi developer yang menambah printer baru?

Latihan 2 — Refactor dengan Interface Kecil

Refactor kode di Latihan 1 agar menerapkan ISP. Wajib menyertakan:

  • Interface Printable, Scannable, Faxable, Copyable.
  • Class SimplePrinter yang hanya implement Printable.
  • Class OfficePrinter yang implement Printable, Scannable, Copyable.
  • Class FaxMachine yang implement Faxable saja.
  • Kode klien yang mendemonstrasikan type-safe usage.

Target: menambah jenis printer baru cukup dengan memilih interface yang relevan.

Latihan 3 — Sistem Pembayaran

Perhatikan hirarki class berikut yang melanggar ISP:

interface PaymentMethod
{
    public function pay(float $amount): string;
    public function refund(float $amount): string;
    public function transfer(float $amount, string $to): string;
}

class CashPayment implements PaymentMethod
{
    public function pay(float $amount): string { return "Bayar tunai: $amount"; }
    public function refund(float $amount): string
    {
        throw new \Exception("Tunai tidak bisa direfund!");
    }
    public function transfer(float $amount, string $to): string
    {
        throw new \Exception("Tunai tidak bisa transfer!");
    }
}

Tugas:

  1. Jelaskan mengapa CashPayment melanggar ISP.
  2. Refactor dengan memisahkan interface: Payable, Refundable, Transferable.
  3. Buat class: CashPayment (hanya Payable), CreditCardPayment (Payable + Refundable), BankTransferPayment (ketiganya).
  4. Tunjukkan bahwa kode klien aman di semua kasus.

Latihan 4 — Bandingkan Interface Gemuk vs Kecil

Ambil satu sistem sederhana yang Anda kenal (misal: sistem perpustakaan atau sistem akademik). Buat dua versi interface:

  1. Versi gemuk — satu interface besar untuk semua peran.
  2. Versi kecil — beberapa interface kecil, masing-masing 1–2 method.

Untuk setiap versi, tulis:

  • Kelebihan dan kekurangan.
  • Bagaimana kode klien di masing-masing versi.
  • Kesimpulan: mana yang akan Anda pilih untuk production, dan mengapa?

Tugas Akhir — Audit ISP pada Project Sebelumnya

Ambil salah satu project PHP Anda yang punya interface, lalu audit ISP:

  1. Identifikasi setiap interface yang punya lebih dari 3 method.
  2. Untuk setiap interface, periksa:
    • Apakah semua implementor memakai semua method?
    • Ada implementor yang mengosongkan method?
    • Ada implementor yang melempar exception?
  3. Refactor dengan memecah interface gemuk menjadi interface kecil.
  4. Buat class diagram sebelum dan sesudah.
  5. Kumpulkan laporan PDF + ZIP project.
