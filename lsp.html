1. Apa Itu Liskov Substitution Principle?

"Objek turunan harus bisa menggantikan objek induknya tanpa merusak program."

— Barbara Liskov (1987)

LSP adalah prinsip ketiga dari SOLID. Intinya: kalau class B adalah turunan class A, maka di mana pun A dipakai, B harus bisa dipakai tanpa error atau perilaku aneh.

Dengan kata lain: turunan tidak boleh "menolak" perilaku induknya. Kalau turunan terpaksa melempar exception di method yang seharusnya berjalan, atau mengosongkan method yang wajib ada, itu tanda LSP dilanggar.

Analogi Sehari-hari Bayangkan Anda punya remote TV universal. Remote ini bisa menggantikan remote TV Samsung, LG, atau Sony — asalkan tombol power, volume, dan channel berfungsi sama.

Kalau ada remote "turunan" yang tombol volume-nya malah melempar error "tidak didukung", Anda tentu kecewa — karena remote itu tidak bisa menggantikan remote asli.

Itulah inti LSP: turunan harus "kompatibel" dengan induknya.

1.1 Definisi Formal (Sederhana)

Barbara Liskov merumuskan:

"Jika S adalah subtipe dari T, maka objek bertipe T dapat digantikan dengan objek bertipe S tanpa mengubah kebenaran program."

Dalam bahasa sehari-hari: kalau kode Anda bekerja dengan Bird, maka kode itu juga harus bekerja dengan Eagle, Penguin, atau turunan apa pun dari Bird — tanpa perlu diubah.

2. Kenapa LSP Penting?

AspekTanpa LSPDengan LSP
Kode klien Harus cek tipe if ($obj instanceof Penguin) Tidak perlu cek — semua turunan bisa dipakai
Kepercayaan pada hirarki Rendah — turunan bisa "berkhianat" Tinggi — semua turunan konsisten
Testing Sulit — tiap turunan punya perilaku aneh Mudah — satu set test berlaku untuk semua
Menambah turunan baru Berisiko — harus cek apakah merusak klien Aman — selama patuh LSP
Refactor Berisiko tinggi Aman, terisolasi
Manfaat Utama LSP menjamin bahwa polimorfisme bekerja dengan benar. Kalau LSP dilanggar, polimorfisme jadi "bumerang" — Anda pikir bisa memperlakukan semua turunan sama, ternyata ada yang melempar exception atau berperilaku beda.

3. Gejala-Gejala Pelanggaran LSP

Kenali tanda-tanda berikut di kode Anda:

  • Ada method di turunan yang melempar exception karena "tidak didukung".
  • Ada method di turunan yang dikosongkan (tidak melakukan apa-apa) padahal induknya melakukan sesuatu.
  • Kode klien sering melakukan if ($obj instanceof SomeType) atau if (get_class($obj) === 'Penguin').
  • Ada switch atau match berdasarkan tipe class turunan.
  • Turunan mengubah arti method induk (misal withdraw() di rekening yang tidak boleh minus malah menambah saldo).
  • Turunan mengubah tipe return menjadi lebih sempit dari yang dijanjikan induk (melanggar kontrak).
  • Ada komentar seperti // jangan panggil method ini untuk class X.
Aturan Cepat Kalau turunan terpaksa meng-override method induk hanya untuk melempar exception atau "mengosongkan" perilaku, itu tanda kuat LSP dilanggar.

Solusinya: pecah interface menjadi lebih kecil, atau ubah hirarki inheritance.

4. Kode yang Melanggar LSP (Studi Kasus Burung)

Kita mulai dengan contoh klasik: Burung (Bird). Secara intuitif, burung bisa terbang. Tapi penguin juga burung — dan penguin tidak bisa terbang.

4.1 Hirarki yang Salah

❌ SALAH — Melanggar LSP 
<?php
// src/Models/Bird.php
namespace App\Models;

class Bird
{
    public function fly(): string
    {
        return "Terbang tinggi!";
    }

    public function eat(): string
    {
        return "Makan.";
    }
}
❌ SALAH — Turunan yang "Menolak" 
<?php
// src/Models/Penguin.php
namespace App\Models;

class Penguin extends Bird
{
    public function fly(): string
    {
        throw new \Exception("Pinguin tidak bisa terbang!");
    }
}
❌ SALAH — Kode Klien yang Rapuh 
<?php
// index.php
require_once __DIR__ . '/vendor/autoload.php';

use App\Models\Bird;
use App\Models\Penguin;
use App\Models\Eagle;

function makeItFly(Bird $bird): void
{
    // Kode ini mengandalkan bahwa SEMUA Bird bisa terbang
    echo $bird->fly() . PHP_EOL;
}

// OK — Eagle bisa terbang
makeItFly(new Eagle());

// BOOM! — Penguin melempar exception
makeItFly(new Penguin());
Hasil Eksekusi 
Terbang tinggi!
PHP Fatal error: Uncaught Exception: Pinguin tidak bisa terbang!
Kode makeItFly() rusak saat diberi Penguin. Padahal Penguin adalah Bird. Inilah pelanggaran LSP.

4.2 Kenapa Ini Melanggar LSP?

Ingat definisi: "Objek turunan harus bisa menggantikan objek induknya tanpa merusak program."

Di kode di atas:

  • makeItFly() menerima parameter Bird — artinya semua turunan Bird harus bisa dipakai di sini.
  • Namun Penguin (turunan Bird) tidak bisa dipakai — dia melempar exception.
  • Berarti Penguin tidak bisa menggantikan Bird. → LSP dilanggar.
Kenapa Ini Terjadi? Karena class Bird menjanjikan bahwa semua burung bisa terbang (lewat method fly()). Tapi kenyataannya tidak semua burung bisa terbang. Janji itu tidak bisa ditepati oleh Penguin.

Solusinya bukan menghapus Penguin, tapi memperbaiki janji (kontrak).

5. Analisis Masalah pada Kode Tersebut

Mari kita bedah: apa yang sebenarnya salah?

NoMasalahPenjelasan
1 Kontrak terlalu luas Bird menjanjikan fly() untuk semua burung. Padahal tidak semua burung bisa terbang.
2 Turunan melempar exception Penguin::fly() melempar exception — artinya turunan menolak perilaku induk.
3 Kode klien rusak makeItFly() yang seharusnya menerima semua Bird, ternyata crash saat diberi Penguin.
4 Polimorfisme tidak bekerja Anda tidak bisa memperlakukan Penguin seperti Bird pada umumnya.

5.1 Dampak Nyata Pelanggaran Ini

  • Kode klien jadi "penuh intaian" — setiap kali memakai Bird, Anda harus cek if ($bird instanceof Penguin).
  • Testing berantakan — test yang sama tidak bisa berlaku untuk semua turunan.
  • Tidak bisa menambah turunan baru tanpa risiko — setiap burung baru, Anda harus cek apakah bisa terbang atau tidak.
  • Melanggar "is-a" relationship — secara sintaks Penguin extends Bird, tapi secara semantik Penguin bukan Bird yang bisa terbang.

6. Refactor: Menerapkan LSP

Solusinya: pisahkan kemampuan "terbang" menjadi interface tersendiri. Tidak semua burung harus bisa terbang — hanya burung yang memang bisa.

1

Interface Bird — Kontrak Minimal

Kontrak dasar semua burung: hanya eat(). Semua burung (termasuk penguin) pasti bisa makan. Ini janji yang bisa ditepati oleh semua.

INTERFACE 
<?php
// src/Contracts/Bird.php
namespace App\Contracts;

interface Bird
{
    public function eat(): string;
}
2

Interface FlyingBird — Kontrak Tambahan

Interface ini extends Bird dan menambahkan kemampuan fly(). Hanya burung yang memang bisa terbang yang mengimplementasi interface ini.

INTERFACE (extends) 
<?php
// src/Contracts/FlyingBird.php
namespace App\Contracts;

interface FlyingBird extends Bird
{
    public function fly(): string;
}
3

Class Eagle — Burung yang Bisa Terbang

Elang mengimplementasi FlyingBird karena memang bisa terbang. Kedua method (eat() dan fly()) diimplementasi dengan benar.

✅ LSP Terpenuhi 
<?php
// src/Models/Eagle.php
namespace App\Models;

use App\Contracts\FlyingBird;

class Eagle implements FlyingBird
{
    public function eat(): string
    {
        return "Makan daging";
    }

    public function fly(): string
    {
        return "Terbang tinggi!";
    }
}
4

Class Penguin — Burung yang Tidak Bisa Terbang

Penguin hanya mengimplementasi Bird, bukan FlyingBird. Dia tidak perlu memaksakan diri punya method fly().

✅ LSP Terpenuhi 
<?php
// src/Models/Penguin.php
namespace App\Models;

use App\Contracts\Bird;

class Penguin implements Bird
{
    public function eat(): string
    {
        return "Makan ikan";
    }

    // Tidak perlu implement fly() — karena memang tidak bisa terbang
}
5

Class Ostrich — Contoh Lain

Burung unta juga tidak bisa terbang. Sama seperti penguin, dia mengimplementasi Bird saja.

✅ LSP Terpenuhi 
<?php
// src/Models/Ostrich.php
namespace App\Models;

use App\Contracts\Bird;

class Ostrich implements Bird
{
    public function eat(): string
    {
        return "Makan tumbuhan";
    }
}
6

Kode Klien — Sekarang Aman

Fungsi feed() menerima Bird — dan semua burung bisa dipakai di sini tanpa error. Fungsi makeItFly() menerima FlyingBird — hanya burung yang bisa terbang.

index.php 
<?php
require_once __DIR__ . '/vendor/autoload.php';

use App\Contracts\Bird;
use App\Contracts\FlyingBird;
use App\Models\Eagle;
use App\Models\Penguin;
use App\Models\Ostrich;

// Fungsi untuk semua burung (aman)
function feed(Bird $bird): void
{
    echo $bird->eat() . PHP_EOL;
}

// Fungsi HANYA untuk burung yang bisa terbang
function makeItFly(FlyingBird $bird): void
{
    echo $bird->fly() . PHP_EOL;
}

// Semua burung bisa makan
feed(new Eagle());     // Makan daging
feed(new Penguin());   // Makan ikan
feed(new Ostrich());   // Makan tumbuhan

// Hanya burung yang bisa terbang
makeItFly(new Eagle());  // Terbang tinggi!

// makeItFly(new Penguin());  // ❌ ERROR COMPILE — memang tidak boleh
// makeItFly(new Ostrich());  // ❌ ERROR COMPILE — memang tidak boleh
Hasil Refactor Sekarang:
  • Bird = janji yang semua burung bisa tepati.
  • FlyingBird = janji tambahan untuk yang memang bisa terbang.
  • Penguin dan Ostrich tidak dipaksa "berbohong" dengan method fly().
  • Kode klien menjadi type-safe — error terdeteksi saat compile, bukan runtime.

7. Penggunaan Class, Interface, Abstract, dan Polimorfisme

Refactor LSP di atas memanfaatkan konsep OOP secara tepat. Berikut ringkasan penggunaan masing-masing konsep:

CLASS
Class Biasa

Eagle, Penguin, Ostrich — masing-masing adalah class konkret yang bisa langsung diinstansiasi dengan new.

Setiap class hanya mengimplementasi kontrak yang memang bisa ditepati.

INTERFACE
Interface

Bird — kontrak minimal semua burung (eat()).
FlyingBird — kontrak tambahan (fly()).

Interface memungkinkan kita memecah kontrak gemuk menjadi kontrak kecil dan spesifik — inilah kunci LSP.

ABSTRACT CLASS
Abstract Class

Pada contoh ini tidak digunakan karena tidak ada logic bersama yang perlu diwarisi. Interface sudah cukup.

(Akan dibahas di bagian 7.1 kapan abstract class tepat dipakai dalam konteks LSP.)

POLIMORFISME
Polimorfisme

feed(Bird $bird) bisa menerima Eagle, Penguin, atau Ostrich — semua berperilaku sesuai kontrak eat().

Inilah polimorfisme yang sehat karena LSP terpenuhi.

7.1 Kapan Pakai Apa? (pada konteks LSP ini)

KebutuhanGunakanContoh di Modul Ini
Kontrak minimal semua turunan Interface Bird dengan eat()
Kontrak tambahan untuk sebagian turunan Interface turunan (extends) FlyingBird extends Bird
Class konkret dengan perilaku spesifik Class Eagle, Penguin, Ostrich
Ada logic bersama + kontrak Abstract class Lihat contoh di bawah (7.2)
Memperlakukan turunan secara seragam Polimorfisme feed(Bird $bird)

7.2 Kapan Abstract Class Dipakai dalam Konteks LSP?

Abstract class juga bisa dipakai untuk menerapkan LSP, asalkan kontraknya jujur. Contoh: kita ingin semua burung punya method getName() dengan format yang konsisten — sekaligus tetap memisahkan kemampuan fly().

ABSTRACT CLASS — Kontrak + Logic Bersama 
<?php
// src/Abstracts/AbstractBird.php
namespace App\Abstracts;

use App\Contracts\Bird;

abstract class AbstractBird implements Bird
{
    public function __construct(protected string $name) {}

    // Method konkret — bisa dipakai semua turunan
    public function getName(): string
    {
        return $this->name;
    }

    // Method abstrak — WAJIB diimplementasi turunan
    abstract public function eat(): string;
}
INTERFACE — Kontrak Tambahan 
<?php
// src/Contracts/FlyingBird.php
namespace App\Contracts;

interface FlyingBird extends Bird
{
    public function fly(): string;
}
✅ Turunan 1 — Bisa Terbang 
<?php
// src/Models/Eagle.php
namespace App\Models;

use App\Abstracts\AbstractBird;
use App\Contracts\FlyingBird;

class Eagle extends AbstractBird implements FlyingBird
{
    public function eat(): string
    {
        return $this->getName() . " makan daging";
    }

    public function fly(): string
    {
        return $this->getName() . " terbang tinggi!";
    }
}
✅ Turunan 2 — Tidak Bisa Terbang 
<?php
// src/Models/Penguin.php
namespace App\Models;

use App\Abstracts\AbstractBird;

class Penguin extends AbstractBird
{
    public function eat(): string
    {
        return $this->getName() . " makan ikan";
    }

    // Tidak implement fly() — karena memang tidak bisa terbang
}

Kode klien:

<?php
use App\Contracts\Bird;
use App\Contracts\FlyingBird;
use App\Models\Eagle;
use App\Models\Penguin;

function feed(Bird $bird): void
{
    echo $bird->eat() . PHP_EOL;
}

function makeItFly(FlyingBird $bird): void
{
    echo $bird->fly() . PHP_EOL;
}

feed(new Eagle('Elang'));
feed(new Penguin('Pinguin'));   // OK — semua Bird punya eat()
makeItFly(new Eagle('Elang'));  // OK — Eagle bisa terbang
// makeItFly(new Penguin('Pinguin'));  // ❌ ERROR COMPILE — tidak boleh
Pola Kombinasi Interface + Abstract Class
  • Interface Bird — kontrak resmi yang bisa di-type-hint.
  • Interface FlyingBird — kontrak tambahan yang spesifik.
  • Abstract class AbstractBird — implementasi umum (logic bersama, property name).
  • Class konkret — implementasi spesifik.
Inilah pola yang paling umum dipakai di framework modern (Laravel, Symfony).

8. Perbandingan Sebelum vs Sesudah

❌ SEBELUM (Melanggar LSP)
  • Satu interface Bird dengan method fly()
  • Penguin::fly() melempar exception
  • Kode klien crash saat diberi Penguin
  • Harus cek instanceof manual
  • Polimorfisme tidak bekerja
  • Tambah burung baru = berisiko
✅ SESUDAH (LSP Terpenuhi)
  • Interface Bird hanya eat()
  • Interface FlyingBird untuk yang bisa terbang
  • Penguin tidak punya fly() — tidak memaksakan diri
  • Kode klien aman, error terdeteksi saat compile
  • Polimorfisme bekerja penuh
  • Tambah burung baru = aman
Aspek❌ Sebelum LSP✅ Sesudah LSP
Jumlah interface 1 (Bird dengan fly()) 2 (Bird, FlyingBird)
Method di Penguin 2 (dengan fly() melempar exception) 1 (hanya eat())
Kode klien Crash saat diberi Penguin Aman, error terdeteksi di compile
Type safety Rendah Tinggi
Polimorfisme Tidak bekerja Bekerja penuh
Menambah burung baru Berisiko Aman

9. Aturan Praktis LSP

Berikut aturan praktis yang bisa Anda hafal untuk menghindari pelanggaran LSP:

AturanPenjelasan
Jangan lempar exception baru Turunan tidak boleh melempar exception yang tidak dilempar induk, untuk method yang sama.
Jangan kosongkan method Kalau induk punya method yang "melakukan sesuatu", turunan tidak boleh mengosongkannya.
Pertahankan kontrak Kalau induk menjanjikan return string, turunan tidak boleh return null.
Jangan perketat parameter Kalau induk menerima int, turunan tidak boleh hanya menerima int > 0.
Jangan longgarkan postcondition Kalau induk menjamin "saldo tidak negatif", turunan tidak boleh membuat saldo negatif.
Pecah interface gemuk Lebih baik banyak interface kecil daripada satu interface besar yang memaksa turunan "berbohong".
Aturan Emas Saat membuat turunan, tanyakan:

"Apakah turunan ini bisa menggantikan induknya di semua tempat tanpa mengubah perilaku program?"

Kalau tidak, berarti ada pelanggaran LSP. Perbaiki hirarki atau pecah interface.

11. Kapan LSP Bisa "Dilonggarkan"?

LSP adalah pedoman, bukan hukum mutlak. Ada situasi di mana penerapan LSP secara ketat justru over-engineering:

SituasiBoleh Dilonggarkan?Alasan
Project kecil (1–3 class) Ya Memecah terlalu banyak interface = overhead tanpa manfaat
Prototyping cepat Ya Fokus ke fungsionalitas dulu, refactor nanti
Hirarki sangat stabil Ya, tapi hati-hati Selama tidak ada turunan baru yang "menolak" perilaku induk
Aplikasi sedang tumbuh Mulai ketat Saat mulai ada banyak if ($obj instanceof X) di kode klien
Tim besar, jangka panjang Wajib LSP ketat Mencegah bug tersembunyi & memudahkan maintenance bertahun-tahun
Hubungan dengan Prinsip Lain LSP sangat erat kaitannya dengan Interface Segregation Principle (I). Saat LSP dilanggar, sering kali solusinya adalah memecah interface gemuk menjadi interface kecil — dan itulah inti ISP.

LSP juga terkait Open/Closed Principle (O): kalau turunan tidak bisa menggantikan induk, maka "menambah turunan" tidak benar-benar menjadi "ekstensi" — melainkan "modifikasi perilaku" yang berisiko.

12. Latihan & Tugas

Latihan 1 — Identifikasi Pelanggaran LSP

Perhatikan kode berikut, lalu jawab pertanyaan:

<?php
class Rectangle
{
    protected float $width;
    protected float $height;

    public function setWidth(float $width): void
    {
        $this->width = $width;
    }

    public function setHeight(float $height): void
    {
        $this->height = $height;
    }

    public function getArea(): float
    {
        return $this->width * $this->height;
    }
}

class Square extends Rectangle
{
    public function setWidth(float $width): void
    {
        $this->width = $width;
        $this->height = $width;  // paksa tinggi = lebar
    }

    public function setHeight(float $height): void
    {
        $this->width = $height;
        $this->height = $height;
    }
}
  1. Mengapa class Square melanggar LSP?
  2. Buat kode klien yang akan crash atau salah hasil saat diberi Square.
  3. Sebutkan minimal 3 cara untuk memperbaikinya.

(Ini adalah contoh klasik "Rectangle-Square Problem" — pelanggaran LSP paling terkenal di dunia OOP.)

Latihan 2 — Refactor Hirarki

Refactor kode di Latihan 1 agar LSP terpenuhi. Pilih salah satu pendekatan:

  • Pendekatan A — Buat abstract class Shape dengan method getArea(). Rectangle dan Square meng-extends Shape secara terpisah.
  • Pendekatan B — Buat interface Shape dengan method getArea(), lalu Rectangle dan Square mengimplementasi interface tersebut secara terpisah.
  • Pendekatan C — Tambahkan interface Resizable hanya untuk shape yang bisa di-resize.

Bandingkan ketiga pendekatan dan pilih mana yang paling tepat untuk kasus ini.

Latihan 3 — Sistem Pembayaran

Perhatikan hirarki class berikut yang melanggar LSP:

abstract class PaymentMethod
{
    abstract public function pay(float $amount): string;
    abstract public function refund(float $amount): string;
}

class CashPayment extends PaymentMethod
{
    public function pay(float $amount): string  { return "Bayar tunai: $amount"; }
    public function refund(float $amount): string
    {
        throw new \Exception("Tunai tidak bisa direfund!");
    }
}

Tugas:

  1. Jelaskan mengapa CashPayment melanggar LSP.
  2. Refactor dengan memisahkan interface Payable dan Refundable.
  3. Buat class: CashPayment (hanya Payable), CreditCardPayment (keduanya), EwalletPayment (keduanya).
  4. Tunjukkan bahwa kode klien aman di semua kasus.

Tugas Akhir — Audit LSP pada Project Sebelumnya

Ambil salah satu project PHP Anda yang punya inheritance (class extends class), lalu audit LSP:

  1. Identifikasi setiap turunan yang meng-override method induknya.
  2. Untuk setiap override, periksa:
    • Apakah turunan melempar exception baru?
    • Apakah turunan mengosongkan perilaku?
    • Apakah turunan mengubah kontrak (return type, parameter)?
  3. Refactor hirarki agar LSP terpenuhi — bisa dengan memecah interface, memakai abstract class, atau mengganti inheritance menjadi komposisi.
  4. Buat class diagram sebelum dan sesudah.
  5. Kumpulkan laporan PDF + ZIP project.
