1. Apa Itu Dependency Inversion Principle?

"Bergantunglah pada abstraksi (interface), bukan pada implementasi konkret."

— Robert C. Martin (Uncle Bob)

DIP adalah prinsip kelima — dan terakhir — dari SOLID. Intinya: class tingkat tinggi (Service) tidak boleh bergantung langsung pada class tingkat rendah (MySQL, Email, File). Keduanya harus bergantung pada interface.

Dengan kata lain: balik arah ketergantungan. Jangan UserService yang "memanggil" MySQLDatabase, tapi UserService menerima DatabaseInterface dari luar.

Analogi Sehari-hari Bayangkan lampu meja yang kabelnya disolder langsung ke stop kontak dinding. Kalau lampu rusak, Anda harus bongkar dinding.

Bandingkan dengan lampu yang pakai colokan standar. Lampu apa pun (Philips, Xiaomi, IKEA) bisa dicolok ke stop kontak yang sama. Kalau lampu rusak, cukup cabut dan ganti — dinding tidak tersentuh.

DIP mengajarkan: buat "colokan standar" (interface), bukan solder langsung.

1.1 Definisi Formal (Sederhana)

"Modul tingkat tinggi tidak boleh bergantung pada modul tingkat rendah. Keduanya harus bergantung pada abstraksi."

Artinya:

  • Modul tingkat tinggi = class yang berisi logika bisnis (misal UserService).
  • Modul tingkat rendah = class yang berisi detail teknis (misal MySQLDatabase, EmailSender, FileLogger).
  • Abstraksi = interface yang menjembatani keduanya (misal DatabaseInterface).

2. Dua Bagian DIP yang Sering Terlewat

DIP sebenarnya terdiri dari dua bagian. Banyak mahasiswa hanya menghafal bagian pertama, padahal bagian kedua sama pentingnya.

NoBagianPenjelasan
1 Modul tingkat tinggi tidak boleh bergantung pada modul tingkat rendah. Keduanya harus bergantung pada abstraksi. Class seperti UserService tidak boleh langsung new MySQLDatabase(). Harus menerima DatabaseInterface.
2 Abstraksi tidak boleh bergantung pada detail. Detail harus bergantung pada abstraksi. Interface DatabaseInterface tidak boleh tahu apa-apa tentang MySQL, PostgreSQL, atau MongoDB. Justru implementasi konkret yang mengikuti interface.
Kesalahan Umum Banyak yang mengira "pakai interface" sudah cukup. Tapi kalau interface-nya sendiri bocor (misal ada method getMysqlConnection()), itu tetap melanggar DIP. Interface harus bersih dari detail teknis.

3. Kenapa DIP Penting?

AspekTanpa DIPDengan DIP
Ganti database Edit UserService, tes ulang semua Cukup buat implementasi interface baru
Unit testing Butuh database sungguhan, mail server sungguhan Cukup mock / in-memory
Kode klien Bergantung pada semua detail teknis Hanya bergantung pada abstraksi
Reuse Sulit — class terkunci ke MySQL Mudah — class bisa dipakai dengan database apa saja
Kolaborasi tim Tim bisnis & tim DBA saling mengunci Bisa kerja paralel lewat interface
Refactor Berisiko tinggi Aman, terisolasi
Manfaat Utama DIP membuat kode fleksibel (mudah diganti), testable (mudah diuji), dan maintainable (mudah dirawat).

Inilah prinsip yang memungkinkan framework modern seperti Laravel punya service container yang otomatis menyuntikkan dependensi.

4. Gejala-Gejala Pelanggaran DIP

Kenali tanda-tanda berikut di kode Anda:

  • Class berisi new MySQLDatabase(), new PHPMailer(), atau new FileLogger() di dalam method.
  • Class meng-import class konkret dari library eksternal (use PHPMailer\PHPMailer\PHPMailer).
  • Ada new untuk class "berat" (database, API client, filesystem) di dalam constructor atau method.
  • Kode klien tahu terlalu banyak detail teknis (misal harus kirim host, user, password database).
  • Tidak bisa di-unit-test tanpa menyiapkan database / mail server / file system sungguhan.
  • Interface bocor — misal getMysqlConnection() atau getPdoHandle().
  • Ada static call seperti Database::connect() atau Mail::send() di dalam class bisnis.
Aturan Cepat Kalau sebuah class "tahu" terlalu banyak tentang bagaimana dependensinya dibuat (host, port, password, library apa), itu tanda DIP dilanggar.

Solusinya: terima dependensi dari luar melalui constructor (Dependency Injection), dengan tipe interface.

5. Kode yang Melanggar DIP (Studi Kasus UserService)

Kita mulai dengan contoh klasik: UserService yang menyimpan user ke database. Perhatikan bagaimana class ini langsung bergantung pada MySQLDatabase.

5.1 Kode SALAH — Bergantung pada Implementasi Konkret

❌ SALAH — Dependensi Konkret Langsung 
<?php
// src/Services/UserService.php
namespace App\Services;

use App\Models\User;
use PDO;
use PHPMailer\PHPMailer\PHPMailer;

class UserService
{
    private PDO $pdo;

    public function __construct()
    {
        // ⚠️ Hardcode dependensi di dalam class
        $this->pdo = new PDO(
            'mysql:host=localhost;dbname=toko',
            'root',
            'rahasia'
        );
    }

    public function createUser(string $name, string $email): User
    {
        $user = new User($name, $email);

        // ⚠️ UserService tahu detail SQL
        $stmt = $this->pdo->prepare(
            "INSERT INTO users (name, email) VALUES (?, ?)"
        );
        $stmt->execute([$name, $email]);

        // ⚠️ UserService juga tahu detail PHPMailer
        $mailer = new PHPMailer();
        $mailer->isSMTP();
        $mailer->Host = 'smtp.gmail.com';
        $mailer->Username = 'noreply@example.com';
        $mailer->Password = 'rahasia';
        $mailer->setFrom('noreply@example.com', 'Toko');
        $mailer->addAddress($email, $name);
        $mailer->Subject = 'Selamat datang';
        $mailer->Body = "Halo $name, akun Anda sudah aktif.";
        $mailer->send();

        return $user;
    }
}

5.2 Kode Klien yang "Tahu Segalanya"

❌ SALAH — Klien Tidak Tahu Apa yang Terjadi 
<?php
// index.php
require_once __DIR__ . '/vendor/autoload.php';

use App\Services\UserService;

// ⚠️ Klien hanya tahu "new UserService()" — tidak tahu bahwa:
// - Service ini butuh MySQL
// - Service ini butuh SMTP Gmail
// - Service ini akan gagal kalau salah satu tidak tersedia
$service = new UserService();

$user = $service->createUser('Budi', 'budi@example.com');
echo "User dibuat: " . $user->getName();
Masalah Utama
  • UserService memilih sendiri database apa yang dipakai.
  • UserService memilih sendiri cara kirim email (PHPMailer, SMTP Gmail).
  • Password database dan SMTP tertanam di dalam class (bahaya keamanan!).
  • Tidak bisa diganti ke PostgreSQL tanpa edit UserService.
  • Tidak bisa di-unit-test tanpa MySQL dan Gmail sungguhan.
  • Melanggar DIP: class tingkat tinggi bergantung langsung pada class tingkat rendah.

6. Analisis Masalah pada Kode Tersebut

Mari kita bedah: apa yang sebenarnya salah?

NoMasalahPenjelasan
1 Arah dependensi salah UserService (tinggi) → PDO (rendah). Seharusnya keduanya → interface.
2 Dependensi konkret new PDO() dan new PHPMailer() langsung di dalam class.
3 Konfigurasi bocor Host, username, password database dan SMTP tertanam di class.
4 Tidak bisa diganti Ganti ke PostgreSQL = edit UserService.
5 Tidak bisa di-test Unit test butuh MySQL dan Gmail sungguhan.
6 Melanggar DIP Modul tingkat tinggi bergantung pada modul tingkat rendah.

6.1 Ilustrasi Arah Dependensi yang Salah

❌ TANPA DIP — Arah Dependensi Salah UserService (tinggi) │ │ bergantung langsung ▼ MySQLDatabase (rendah) │ ▼ PDO ⚠️ Kalau MySQLDatabase berubah, UserService harus ikut diubah.
✅ DENGAN DIP — Arah Dependensi Dibalik UserService (tinggi) │ │ bergantung pada ▼ DatabaseInterface ◄──── MySQLDatabase (rendah) ◄──── PostgreSQLDatabase ◄──── InMemoryDatabase ✅ UserService tidak tahu MySQL. MySQLDatabase mengikuti interface.

6.2 Dampak Nyata Pelanggaran Ini

  • Vendor lock-in — begitu pakai MySQL, susah pindah ke PostgreSQL atau MongoDB tanpa bongkar UserService.
  • Testing mustahil — setiap unit test harus siapkan MySQL dan Gmail sungguhan. Test jadi lambat dan rapuh.
  • Keamanan terancam — password database dan SMTP tertanam di kode, rawan bocor kalau repo di-push ke publik.
  • Kolaborasi terhambat — tim bisnis dan tim DBA tidak bisa kerja paralel karena saling mengunci.
  • Tidak reusable — UserService tidak bisa dipakai di project lain yang pakai database berbeda.

7. Refactor: Menerapkan DIP dengan Dependency Injection

Solusinya: balik arah ketergantungan. Buat interface untuk setiap dependensi, lalu terima dependensi itu dari luar melalui constructor. Inilah yang disebut Dependency Injection.

1

Interface DatabaseInterface — Abstraksi Database

Kontrak minimal yang dibutuhkan UserService. Bebas dari detail teknis — tidak boleh ada getMysqlConnection() di sini.

INTERFACE 
<?php
// src/Contracts/DatabaseInterface.php
namespace App\Contracts;

interface DatabaseInterface
{
    public function insert(string $table, array $data): bool;
    public function find(string $table, int $id): ?array;
}
2

Interface MailerInterface — Abstraksi Pengiriman Email

Kontrak minimal untuk kirim email. Bebas dari detail PHPMailer, SMTP, atau API apa pun.

INTERFACE 
<?php
// src/Contracts/MailerInterface.php
namespace App\Contracts;

interface MailerInterface
{
    public function send(string $to, string $subject, string $body): bool;
}
3

Implementasi MySQLDatabase — Detail Teknis

Kelas konkret yang mengikuti interface. Di sini boleh ada detail PDO, SQL, host, password — karena ini memang "dunia teknis".

✅ Implementasi Interface 
<?php
// src/Database/MySQLDatabase.php
namespace App\Database;

use App\Contracts\DatabaseInterface;
use PDO;

class MySQLDatabase implements DatabaseInterface
{
    public function __construct(private PDO $pdo) {}

    public function insert(string $table, array $data): bool
    {
        $columns = implode(', ', array_keys($data));
        $placeholders = implode(', ', array_fill(0, count($data), '?'));

        $stmt = $this->pdo->prepare(
            "INSERT INTO {$table} ({$columns}) VALUES ({$placeholders})"
        );
        return $stmt->execute(array_values($data));
    }

    public function find(string $table, int $id): ?array
    {
        $stmt = $this->pdo->prepare(
            "SELECT * FROM {$table} WHERE id = ?"
        );
        $stmt->execute([$id]);
        $row = $stmt->fetch(PDO::FETCH_ASSOC);
        return $row === false ? null : $row;
    }
}
4

Implementasi InMemoryDatabase — Untuk Testing

Implementasi palsu yang tidak butuh database sungguhan. Inilah kekuatan DIP: UserService bisa diuji tanpa MySQL.

✅ Implementasi Interface (Testing) 
<?php
// src/Database/InMemoryDatabase.php
namespace App\Database;

use App\Contracts\DatabaseInterface;

class InMemoryDatabase implements DatabaseInterface
{
    private array $tables = [];

    public function insert(string $table, array $data): bool
    {
        $this->tables[$table][] = $data;
        return true;
    }

    public function find(string $table, int $id): ?array
    {
        return $this->tables[$table][$id - 1] ?? null;
    }
}
5

Implementasi SmtpMailer — Detail Teknis Email

Di sini detail SMTP boleh muncul — karena ini implementasi konkret.

✅ Implementasi Interface 
<?php
// src/Mail/SmtpMailer.php
namespace App\Mail;

use App\Contracts\MailerInterface;
use PHPMailer\PHPMailer\PHPMailer;

class SmtpMailer implements MailerInterface
{
    public function __construct(
        private string $host,
        private string $username,
        private string $password
    ) {}

    public function send(string $to, string $subject, string $body): bool
    {
        $mailer = new PHPMailer();
        $mailer->isSMTP();
        $mailer->Host     = $this->host;
        $mailer->Username = $this->username;
        $mailer->Password = $this->password;
        $mailer->setFrom($this->username, 'Toko');
        $mailer->addAddress($to);
        $mailer->Subject = $subject;
        $mailer->Body    = $body;

        return $mailer->send();
    }
}
6

Class UserService — Sekarang Bersih

Perhatikan: UserService tidak tahu MySQL, tidak tahu SMTP. Dia hanya tahu interface. Dependensi diterima dari luar lewat constructor — inilah Dependency Injection.

✅ DIP Terpenuhi 
<?php
// src/Services/UserService.php
namespace App\Services;

use App\Contracts\DatabaseInterface;
use App\Contracts\MailerInterface;
use App\Models\User;

class UserService
{
    public function __construct(
        private DatabaseInterface $db,
        private MailerInterface   $mailer
    ) {}

    public function createUser(string $name, string $email): User
    {
        $user = new User($name, $email);

        $this->db->insert('users', [
            'name'  => $name,
            'email' => $email,
        ]);

        $this->mailer->send(
            $email,
            'Selamat datang',
            "Halo {$name}, akun Anda sudah aktif."
        );

        return $user;
    }
}
7

Kode Klien — Rangkai dari Luar

Klien (biasanya index.php atau file konfigurasi framework) yang bertugas merangkai dependensi. Inilah yang disebut Composition Root.

index.php — Produksi 
<?php
require_once __DIR__ . '/vendor/autoload.php';

use App\Contracts\DatabaseInterface;
use App\Contracts\MailerInterface;
use App\Database\MySQLDatabase;
use App\Mail\SmtpMailer;
use App\Services\UserService;

// ============ PRODUKSI ============
$pdo        = new PDO('mysql:host=localhost;dbname=toko', 'root', 'rahasia');
$db         = new MySQLDatabase($pdo);
$mailer     = new SmtpMailer('smtp.gmail.com', 'noreply@example.com', 'rahasia');
$service    = new UserService($db, $mailer);

$user = $service->createUser('Budi', 'budi@example.com');
echo "User dibuat: " . $user->getName();
test.php — Testing (Tanpa Database & SMTP) 
<?php
require_once __DIR__ . '/vendor/autoload.php';

use App\Database\InMemoryDatabase;
use App\Mail\FakeMailer;
use App\Services\UserService;

// ============ TESTING ============
$db      = new InMemoryDatabase();
$mailer  = new FakeMailer();  // tidak kirim email sungguhan
$service = new UserService($db, $mailer);

$user = $service->createUser('Budi', 'budi@example.com');

// Assert: user berhasil dibuat tanpa MySQL & Gmail
assert($user->getName() === 'Budi');
assert($mailer->wasSentTo('budi@example.com'));

echo "✅ Semua test lulus!";
Hasil Refactor Sekarang:
  • UserService tidak tahu MySQL — hanya tahu DatabaseInterface.
  • UserService tidak tahu SMTP — hanya tahu MailerInterface.
  • Ganti database? Cukup buat implementasi interface baru.
  • Testing? Cukup pakai InMemoryDatabase dan FakeMailer.
  • Password tidak lagi tertanam di class bisnis — pindah ke file konfigurasi.

8. Penggunaan Class, Interface, Abstract, dan Polimorfisme

Refactor DIP di atas memanfaatkan konsep OOP secara tepat. Berikut ringkasan penggunaan masing-masing konsep:

CLASS
Class Biasa

MySQLDatabase, InMemoryDatabase, SmtpMailer, FakeMailer, UserService.

Class konkret yang bisa diinstansiasi — tapi tidak saling mengenal langsung; mereka bertemu di interface.

INTERFACE
Interface (Inti DIP)

DatabaseInterface dan MailerInterface — kontrak abstrak yang menjadi titik temu antara class tingkat tinggi dan tingkat rendah.

Inilah "colokan standar" yang membuat DIP bekerja.

ABSTRACT CLASS
Abstract Class

Pada contoh ini tidak digunakan karena tidak ada logic bersama yang perlu diwarisi. Interface sudah cukup.

(Akan dibahas di bagian 8.1 kapan abstract class tepat dipakai dalam konteks DIP.)

POLIMORFISME
Polimorfisme

UserService memanggil $this->db->insert() — entah itu MySQLDatabase, PostgreSQLDatabase, atau InMemoryDatabase, pemanggilan tetap sama.

Inilah polimorfisme yang menjadi fondasi DIP.

8.1 Kapan Abstract Class Dipakai dalam Konteks DIP?

Abstract class juga bisa dipakai sebagai abstraksi dependensi, asalkan tetap bersih dari detail teknis. Contoh: kita ingin semua logger punya method log() dengan format konsisten.

ABSTRACT CLASS — Kontrak + Logic Bersama 
<?php
// src/Abstracts/AbstractLogger.php
namespace App\Abstracts;

abstract class AbstractLogger
{
    // Method abstrak — WAJIB diimplementasi turunan
    abstract protected function write(string $formatted): void;

    // Method konkret — bisa dipakai semua turunan
    public function log(string $level, string $message): void
    {
        $formatted = sprintf(
            "[%s] %s: %s",
            date('Y-m-d H:i:s'),
            strtoupper($level),
            $message
        );
        $this->write($formatted);
    }
}
✅ Implementasi Konkret 1 — File 
<?php
// src/Loggers/FileLogger.php
namespace App\Loggers;

use App\Abstracts\AbstractLogger;

class FileLogger extends AbstractLogger
{
    public function __construct(private string $logFile) {}

    protected function write(string $formatted): void
    {
        file_put_contents($this->logFile, $formatted . PHP_EOL, FILE_APPEND);
    }
}
✅ Implementasi Konkret 2 — Database 
<?php
// src/Loggers/DatabaseLogger.php
namespace App\Loggers;

use App\Abstracts\AbstractLogger;
use App\Contracts\DatabaseInterface;

class DatabaseLogger extends AbstractLogger
{
    public function __construct(private DatabaseInterface $db) {}

    protected function write(string $formatted): void
    {
        $this->db->insert('logs', ['message' => $formatted]);
    }
}

Class klien menerima abstract class:

<?php
// src/Services/OrderService.php
namespace App\Services;

use App\Abstracts\AbstractLogger;
use App\Contracts\DatabaseInterface;

class OrderService
{
    public function __construct(
        private DatabaseInterface $db,
        private AbstractLogger    $logger
    ) {}

    public function createOrder(array $data): void
    {
        $this->db->insert('orders', $data);
        $this->logger->log('info', 'Order dibuat');
    }
}
Pola Kombinasi Interface + Abstract Class untuk DIP
  • Interface DatabaseInterface — kontrak murni, bebas detail teknis.
  • Abstract class AbstractLogger — kontrak + logic bersama (format pesan).
  • Class konkret — implementasi detail (PDO, file, dll.).
Ini pola standar di framework modern. Selama interface/abstract class tidak bocor detail teknis, DIP tetap terpenuhi.

9. Perbandingan Sebelum vs Sesudah

❌ SEBELUM (Melanggar DIP)
  • UserService langsung new PDO()
  • UserService langsung new PHPMailer()
  • Password tertanam di kode
  • Ganti database = edit UserService
  • Tidak bisa di-unit-test
  • Kode klien buta — tidak tahu dependensi apa yang dibutuhkan
✅ SESUDAH (DIP Terpenuhi)
  • UserService menerima DatabaseInterface
  • UserService menerima MailerInterface
  • Password dipindah ke file konfigurasi
  • Ganti database = buat implementasi baru
  • Bisa di-unit-test dengan InMemoryDatabase
  • Kode klien eksplisit — jelas dependensi apa yang dibutuhkan
Aspek❌ Sebelum DIP✅ Sesudah DIP
Arah dependensi Service → MySQL (langsung) Service → Interface ← MySQL
Pembuatan dependensi Di dalam class (new) Di luar class (constructor injection)
Ganti database Edit UserService Buat implementasi interface baru
Testing Butuh MySQL + Gmail sungguhan Cukup InMemoryDatabase + FakeMailer
Keamanan Password di class bisnis Password di file konfigurasi
Reuse Terkunci ke MySQL Bisa dipakai dengan database apa saja

10. Aturan Praktis DIP

Berikut aturan praktis yang bisa Anda hafal untuk menerapkan DIP:

AturanPenjelasan
Jangan new dependensi di dalam class Terima dari luar lewat constructor (Dependency Injection).
Type-hint dengan interface Constructor menerima DatabaseInterface, bukan MySQLDatabase.
Interface harus "bersih" Jangan ada getMysqlConnection() — itu detail teknis.
Composition Root Rangkai semua dependensi di satu tempat (misal index.php atau file container).
Konfigurasi bukan kode Password, host, port disimpan di .env atau file config, bukan di class.
Gunakan service container Di framework modern (Laravel, Symfony), container otomatis melakukan DI berdasarkan type-hint constructor.
Aturan Emas Saat menulis class, tanyakan:

"Apakah class ini tahu terlalu banyak tentang bagaimana dependensinya dibuat?"

Kalau ya, berarti DIP dilanggar. Pindahkan pembuatan dependensi ke luar class.

12. Kaitan dengan Prinsip SOLID Lain

DIP adalah prinsip puncak dari SOLID — ia mengikat semua prinsip sebelumnya menjadi satu kesatuan utuh:

PrinsipKaitan dengan DIP
S — Single Responsibility DIP mendorong SRP: Service hanya urus logika bisnis, tidak urus cara koneksi database.
O — Open/Closed DIP memungkinkan OCP: menambah database baru = tambah class implementasi, tanpa ubah Service.
L — Liskov Substitution DIP membutuhkan LSP: implementasi interface harus bisa saling menggantikan tanpa error.
I — Interface Segregation DIP membutuhkan ISP: interface harus kecil dan spesifik, supaya Service tidak dipaksa depend pada method yang tidak dipakai.
D — Dependency Inversion Puncak — menyatukan semua prinsip menjadi pola "bergantung pada abstraksi".
DIP dan Framework Modern DIP adalah prinsip yang paling terlihat efeknya di framework:
  • Laravel — service container otomatis melakukan DI berdasarkan type-hint.
  • Symfony — dependency injection container dengan konfigurasi YAML/XML.
  • Slim — PHP-DI untuk container.
Tanpa DIP, framework tidak mungkin "menyuntikkan" dependensi secara otomatis.

13. Latihan & Tugas

Latihan 1 — Identifikasi Pelanggaran DIP

Perhatikan class berikut, lalu jawab pertanyaan:

<?php
class OrderService
{
    public function process(array $order): void
    {
        // Kirim email langsung
        $mailer = new \PHPMailer\PHPMailer\PHPMailer();
        $mailer->isSMTP();
        $mailer->Host = 'smtp.gmail.com';
        $mailer->Username = 'noreply@example.com';
        $mailer->Password = 'rahasia';
        $mailer->addAddress($order['email']);
        $mailer->Subject = 'Order dikonfirmasi';
        $mailer->Body = 'Terima kasih!';
        $mailer->send();

        // Simpan log langsung
        file_put_contents('/var/log/order.log', date('Y-m-d') . " order diproses\n", FILE_APPEND);
    }
}

  2. Mengapa password SMTP tertanam di class berbahaya?
  3. Bagaimana Anda akan menguji class ini tanpa Gmail?

Latihan 2 — Refactor dengan Interface + DI

Refactor OrderService di atas agar menerapkan DIP. Wajib menyertakan:

  • Interface MailerInterface dengan method send().
  • Interface LoggerInterface dengan method log().
  • Implementasi SmtpMailer dan FileLogger.
  • Implementasi FakeMailer dan InMemoryLogger untuk testing.
  • Class OrderService yang menerima kedua interface di constructor.
  • File index.php (produksi) dan test.php (testing).

Target: OrderService bisa diuji tanpa Gmail dan tanpa filesystem sungguhan.

Latihan 3 — Service Container Sederhana

Buat class Container yang bisa:

  1. Mendaftarkan binding: $container->bind(DatabaseInterface::class, MySQLDatabase::class);
  2. Me-resolve dependensi otomatis berdasarkan type-hint constructor.
  3. Melempar exception jika binding tidak ditemukan.

Petunjuk: gunakan ReflectionClass untuk membaca parameter constructor, lalu resolve satu per satu. Ini adalah miniatur service container Laravel.

Latihan 4 — Bandingkan 3 Pendekatan

Buat implementasi yang sama (misal UserService) dengan 3 pendekatan:

  1. Tanpa DIP — hardcode new PDO() di dalam class.
  2. DIP dengan interface saja — constructor menerima DatabaseInterface.
  3. DIP + abstract class — constructor menerima AbstractDatabase (dengan logic bersama).

Untuk setiap pendekatan, tulis:

  • Kelebihan dan kekurangan.
  • Bagaimana unit-testing masing-masing.
  • Kesimpulan: mana yang akan Anda pilih untuk production, dan mengapa?

Tugas Akhir — Audit DIP pada Project Sebelumnya

Ambil salah satu project PHP Anda yang punya class dengan new Something() di dalamnya. Lakukan audit DIP:

  1. Identifikasi setiap dependensi konkret yang dibuat di dalam class.
  2. Untuk setiap dependensi, tentukan:
    • Apakah layak dibuat interface?
    • Apa dampaknya jika diganti?
    • Bagaimana cara testing-nya?
  3. Refactor dengan menambahkan interface + Dependency Injection.
  4. Buat class diagram sebelum dan sesudah.
  5. Kumpulkan laporan PDF + ZIP project.
