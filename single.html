1. Apa Itu Single Responsibility Principle?

"Setiap class hanya boleh memiliki satu alasan untuk berubah."

— Robert C. Martin (Uncle Bob)

SRP adalah prinsip pertama dari SOLID. Intinya: sebuah class harus punya satu tanggung jawab saja. Kalau class punya banyak tanggung jawab, berarti class itu punya banyak alasan untuk berubah — dan itulah tanda pelanggaran SRP.

Analogi Sehari-hari Bayangkan tukang bangunan serbaguna yang juga merangkap tukang listrik, tukang pipa, tukang cat, dan desainer interior dalam satu orang. Kalau ada satu pekerjaan yang bermasalah, seluruh proyek tersendat.

Bandingkan dengan tim spesialis: tukang batu, tukang listrik, tukang cat — masing-masing ahli di bidangnya. Kalau tukang listrik cuti, tukang batu tetap bekerja.

SRP mengajarkan cara "membentuk tim spesialis" dalam class.

1.1 Cara Menentukan "Satu Tanggung Jawab"

Cara paling mudah: tanyakan "Siapa yang akan meminta saya mengubah class ini?"

Peminta PerubahanAlasanTanggung Jawab
Tim Marketing Aturan diskon berubah Perhitungan diskon
Tim DBA Skema database berubah Penyimpanan data
Tim Validasi Aturan validasi email berubah Validasi input
Tim Email Pindah dari SMTP ke API Pengiriman notifikasi
Aturan Praktis Kalau satu class punya lebih dari satu peminta perubahan, itu tanda SRP dilanggar. Pisahkan menjadi beberapa class.

2. Kenapa SRP Penting?

AspekSebelum SRPSesudah SRP
Membaca kode Satu file panjang, harus baca semua Satu file = satu tujuan, langsung paham
Menambah fitur Edit class besar, rawan merusak yang lain Tambah class kecil, class lama tidak tersentuh
Testing Harus setup seluruh dependensi Unit test fokus pada satu tanggung jawab
Bug Sulit dilacak, semua bercampur Cepat ketemu, jelas lokasinya
Kolaborasi tim Sering konflik Git di satu file Masing-masing pegang file sendiri
Refactor Berisiko tinggi Aman, terisolasi

3. Gejala-Gejala Pelanggaran SRP

Kenali tanda-tanda berikut di kode Anda:

  • Class lebih dari 200 baris.
  • Nama class mengandung kata "Manager" atau "Processor" atau "Handler" — biasanya jendela multi-tugas.
  • Sering muncul komentar pemisah: // === VALIDASI ===, // === SIMPAN ===.
  • Class punya lebih dari 5 method yang tidak saling berkaitan.
  • Anda sering bilang: "Jangan diutak-atik class itu, nanti rusak yang lain".
  • Satu class punya import/dependensi ke library yang tidak berhubungan (email + database + PDF sekaligus).

4. Kode yang Melanggar SRP (Studi Kasus)

Kita akan buat sistem pemesanan sederhana yang memproses order. Perhatikan kode berikut — ini contoh kode yang SALAH karena satu class melakukan terlalu banyak hal.

❌ SALAH — Melanggar SRP 
<?php

// src/OrderProcessor.php
namespace App;

use PDO;

class OrderProcessor
{
    private PDO $pdo;
    private array $order;

    public function __construct(PDO $pdo, array $order)
    {
        $this->pdo   = $pdo;
        $this->order = $order;
    }

    // ============================================
    // TANGGUNG JAWAB 1: Validasi data order
    // ============================================
    public function validate(): bool
    {
        if (empty($this->order['items'])) {
            return false;
        }
        if (empty($this->order['customer_email'])) {
            return false;
        }
        if (!filter_var($this->order['customer_email'], FILTER_VALIDATE_EMAIL)) {
            return false;
        }
        foreach ($this->order['items'] as $item) {
            if (!isset($item['qty']) || $item['qty'] <= 0) {
                return false;
            }
        }
        return true;
    }

    // ============================================
    // TANGGUNG JAWAB 2: Hitung total harga
    // ============================================
    public function calculateTotal(): float
    {
        $total = 0;
        foreach ($this->order['items'] as $item) {
            $total += $item['price'] * $item['qty'];
        }
        // Tambah pajak 11%
        $total = $total * 1.11;
        return $total;
    }

    // ============================================
    // TANGGUNG JAWAB 3: Simpan ke database
    // ============================================
    public function save(): void
    {
        $stmt = $this->pdo->prepare(
            "INSERT INTO orders (customer_email, total, created_at)
             VALUES (?, ?, NOW())"
        );
        $stmt->execute([
            $this->order['customer_email'],
            $this->calculateTotal()
        ]);
    }

    // ============================================
    // TANGGUNG JAWAB 4: Kirim email konfirmasi
    // ============================================
    public function sendConfirmationEmail(): void
    {
        $to      = $this->order['customer_email'];
        $subject = "Konfirmasi Pesanan";
        $message = "Terima kasih! Total pesanan Anda: Rp " .
                   number_format($this->calculateTotal(), 0, ',', '.');
        mail($to, $subject, $message);
    }

    // ============================================
    // TANGGUNG JAWAB 5: Cetak invoice PDF
    // ============================================
    public function generateInvoice(): string
    {
        $html  = "<h1>INVOICE</h1>";
        $html .= "<p>Customer: " . $this->order['customer_email'] . "</p>";
        $html .= "<p>Total: Rp " . number_format($this->calculateTotal(), 0, ',', '.') . "</p>";

        // Simulasi generate PDF
        return $html;
    }

    // ============================================
    // TANGGUNG JAWAB 6: Log aktivitas
    // ============================================
    public function log(string $message): void
    {
        file_put_contents(
            __DIR__ . '/../logs/order.log',
            date('[Y-m-d H:i:s] ') . $message . PHP_EOL,
            FILE_APPEND
        );
    }
}

Cara pakai di index.php:

<?php
require_once __DIR__ . '/vendor/autoload.php';

use App\OrderProcessor;

$pdo = new PDO('mysql:host=localhost;dbname=toko', 'root', '');

$order = [
    'customer_email' => 'budi@example.com',
    'items' => [
        ['name' => 'Laptop', 'price' => 7500000, 'qty' => 1],
        ['name' => 'Mouse',  'price' => 150000,  'qty' => 2],
    ]
];

$processor = new OrderProcessor($pdo, $order);

if ($processor->validate()) {
    $processor->save();
    $processor->sendConfirmationEmail();
    echo $processor->generateInvoice();
    $processor->log("Order baru dibuat");
}

5. Analisis Masalah pada Kode Tersebut

Mari kita bedah: berapa tanggung jawab yang dimiliki OrderProcessor?

NoMethodTanggung JawabSiapa yang Minta Ubah?
1validate()Validasi inputTim bisnis / QA
2calculateTotal()Hitungan pajak & diskonTim keuangan
3save()Penyimpanan databaseTim DBA
4sendConfirmationEmail()Pengiriman emailTim email / SMTP
5generateInvoice()Format PDFTim desain dokumen
6log()LoggingTim DevOps
Hasilnya: 6 Alasan untuk Berubah Satu class punya 6 alasan berbeda untuk diubah. Kalau tim desain minta ubah format invoice, Anda edit file ini. Kalau tim DBA ubah skema database, Anda edit file yang sama. Kalau aturan validasi berubah, edit file yang sama juga.

Inilah pelanggaran SRP yang paling klasik.

5.1 Dampak Nyata Pelanggaran Ini

  • Regresi bug — saat mengubah sendConfirmationEmail() untuk pakai API, tanpa sadar merusak save() di file yang sama.
  • Konflik Git — 3 developer bekerja di satu file, saling tabrak.
  • Testing mustahil — mau tes calculateTotal() harus siapkan PDO, mail server, file system.
  • Reuse tidak mungkin — mau pakai generateInvoice() di project lain? Harus copy-paste seluruh class.
  • Ketergantungan library — class butuh PDO, mail(), file_put_contents() sekaligus — padahal masing-masing adalah "dunia" berbeda.

6. Refactor: Menerapkan SRP

Sekarang kita pecah OrderProcessor menjadi 6 class kecil, masing-masing dengan satu tanggung jawab.

1

Class Order — Model Data

Hanya bertugas menyimpan data order. Tidak ada logika bisnis.

✅ SRP 
<?php
// src/Models/Order.php
namespace App\Models;

class Order
{
    public function __construct(
        private string $customerEmail,
        private array  $items
    ) {}

    public function getCustomerEmail(): string
    {
        return $this->customerEmail;
    }

    public function getItems(): array
    {
        return $this->items;
    }
}
2

Class OrderValidator — Validasi

Hanya bertugas memvalidasi order. Kalau aturan validasi berubah, hanya class ini yang diubah.

✅ SRP 
<?php
// src/Validators/OrderValidator.php
namespace App\Validators;

use App\Models\Order;

class OrderValidator
{
    public function isValid(Order $order): bool
    {
        if (empty($order->getItems())) {
            return false;
        }

        if (!filter_var($order->getCustomerEmail(), FILTER_VALIDATE_EMAIL)) {
            return false;
        }

        foreach ($order->getItems() as $item) {
            if (!isset($item['qty']) || $item['qty'] <= 0) {
                return false;
            }
        }

        return true;
    }
}
3

Class PriceCalculator — Hitung Total

Hanya bertugas menghitung total harga + pajak. Terpisah dari database dan email.

✅ SRP 
<?php
// src/Services/PriceCalculator.php
namespace App\Services;

use App\Models\Order;

class PriceCalculator
{
    private const TAX_RATE = 0.11; // PPN 11%

    public function calculateTotal(Order $order): float
    {
        $subtotal = 0;
        foreach ($order->getItems() as $item) {
            $subtotal += $item['price'] * $item['qty'];
        }

        return $subtotal * (1 + self::TAX_RATE);
    }
}
4

Interface OrderRepositoryInterface — Kontrak Penyimpanan

Gunakan interface agar bisa ganti dari MySQL ke PostgreSQL atau ke in-memory untuk testing, tanpa mengubah class lain.

INTERFACE 
<?php
// src/Contracts/OrderRepositoryInterface.php
namespace App\Contracts;

use App\Models\Order;

interface OrderRepositoryInterface
{
    public function save(Order $order, float $total): int;
}
5

Class MySQLOrderRepository — Implementasi Database

Implementasi konkret interface. Hanya bertugas berbicara dengan MySQL.

✅ SRP + Interface 
<?php
// src/Repositories/MySQLOrderRepository.php
namespace App\Repositories;

use App\Contracts\OrderRepositoryInterface;
use App\Models\Order;
use PDO;

class MySQLOrderRepository implements OrderRepositoryInterface
{
    public function __construct(private PDO $pdo) {}

    public function save(Order $order, float $total): int
    {
        $stmt = $this->pdo->prepare(
            "INSERT INTO orders (customer_email, total, created_at)
             VALUES (?, ?, NOW())"
        );
        $stmt->execute([$order->getCustomerEmail(), $total]);

        return (int) $this->pdo->lastInsertId();
    }
}
6

Abstract Class Notifier — Basis Pengiriman Notifikasi

Gunakan abstract class karena ada logic bersama (format pesan) yang bisa diwarisi oleh semua notifier. Method send() tetap abstrak — wajib diimplementasi turunannya.

ABSTRACT CLASS 
<?php
// src/Notifications/Notifier.php
namespace App\Notifications;

use App\Models\Order;

abstract class Notifier
{
    // Method abstrak — WAJIB diimplementasi turunan
    abstract public function send(Order $order, float $total): void;

    // Method konkret — BISA dipakai semua turunan (logic bersama)
    protected function buildMessage(Order $order, float $total): string
    {
        return "Halo " . $order->getCustomerEmail() .
               ", pesanan Anda dengan total Rp " .
               number_format($total, 0, ',', '.') .
               " telah diterima.";
    }
}
7

Class EmailNotifier — Implementasi Email

Turunan dari Notifier. Hanya bertugas kirim lewat email.

✅ SRP + Abstract + Polymorphism 
<?php
// src/Notifications/EmailNotifier.php
namespace App\Notifications;

use App\Models\Order;

class EmailNotifier extends Notifier
{
    public function send(Order $order, float $total): void
    {
        $message = $this->buildMessage($order, $total);
        mail($order->getCustomerEmail(), "Konfirmasi Pesanan", $message);
    }
}
8

Class WhatsAppNotifier — Implementasi WhatsApp

Turunan lain dari Notifier. Bisa ditambahkan tanpa ubah class lain.

✅ SRP + Abstract + Polymorphism 
<?php
// src/Notifications/WhatsAppNotifier.php
namespace App\Notifications;

use App\Models\Order;

class WhatsAppNotifier extends Notifier
{
    public function send(Order $order, float $total): void
    {
        $message = $this->buildMessage($order, $total);
        // simulasi kirim WhatsApp
        error_log("[WA] " . $message);
    }
}

11

Class OrderService — Koordinator

Class ini adalah "konduktor" yang merangkai semua komponen di atas. Ia tidak menghitung, tidak menyimpan langsung, tidak mengirim — ia hanya mengoordinasikan. Itulah satu-satunya tanggung jawabnya.

✅ SRP sebagai Orkestrator 
<?php
// src/Services/OrderService.php
namespace App\Services;

use App\Models\Order;
use App\Validators\OrderValidator;
use App\Contracts\OrderRepositoryInterface;
use App\Notifications\Notifier;
use App\Services\InvoiceGenerator;
use App\Services\Logger;
use InvalidArgumentException;

class OrderService
{
    public function __construct(
        private OrderValidator          $validator,
        private PriceCalculator         $calculator,
        private OrderRepositoryInterface $repository,
        private Notifier                $notifier,
        private InvoiceGenerator        $invoice,
        private Logger                  $logger
    ) {}

    public function process(Order $order): string
    {
        // 1. Validasi
        if (!$this->validator->isValid($order)) {
            throw new InvalidArgumentException("Order tidak valid");
        }

        // 2. Hitung total
        $total = $this->calculator->calculateTotal($order);

        // 3. Simpan
        $this->repository->save($order, $total);

        // 4. Kirim notifikasi
        $this->notifier->send($order, $total);

        // 5. Log
        $this->logger->log("Order untuk {$order->getCustomerEmail()} dibuat");

        // 6. Return invoice
        return $this->invoice->generateHtml($order, $total);
    }
}

index.php

7. Penggunaan Class, Interface, Abstract, dan Polimorfisme

Refactor SRP di atas memanfaatkan semua pilar OOP secara bersamaan. Berikut ringkasan penggunaan masing-masing konsep:

CLASS
Class Biasa

Order, OrderValidator, PriceCalculator, InvoiceGenerator, Logger, MySQLOrderRepository, EmailNotifier, WhatsAppNotifier.

Semua adalah class konkret yang bisa langsung diinstansiasi dengan new. Setiap class punya satu tanggung jawab.

INTERFACE
Interface

OrderRepositoryInterface — kontrak untuk semua repository.

Memungkinkan ganti dari MySQL ke PostgreSQL atau in-memory tanpa ubah OrderService. Ini sekaligus penerapan Dependency Inversion.

ABSTRACT CLASS
Abstract Class

Notifier — dasar untuk semua jenis notifikasi.

Berisi method konkret buildMessage() yang bisa dipakai ulang oleh semua turunan, dan method abstrak send() yang wajib diimplementasi.

POLIMORFISME
Polimorfisme

OrderService menerima parameter Notifier $notifier, bisa diisi EmailNotifier atau WhatsAppNotifier.

Method send() dipanggil sama, tapi perilaku berbeda tergantung objek konkretnya. Inilah esensi polimorfisme.

7.1 Kapan Pakai Apa? (pada konteks SRP ini)

KebutuhanGunakanContoh di Modul Ini
Objek dengan data Class Order
Logika tunggal tanpa state Class OrderValidator, PriceCalculator
Butuh ganti implementasi nanti Interface OrderRepositoryInterface
Ada logic bersama + kontrak Abstract class Notifier
Beberapa varian perilaku Polimorfisme EmailNotifier, WhatsAppNotifier

10. Kapan SRP Bisa "Dilonggarkan"?

SRP adalah pedoman, bukan hukum mutlak. Ada situasi di mana menerapkan SRP secara ketat justru over-engineering:

SituasiBoleh DigabungAlasan
Project kecil (1–3 file) Ya Memecah terlalu banyak class = overhead tanpa manfaat
Prototyping cepat Ya Fokus ke fungsionalitas dulu, refactor nanti
Class data polos (DTO) Ya Class Order hanya berisi property & getter — tidak perlu dipecah lagi
Aplikasi sedang tumbuh Mulai pisahkan Saat class melebihi 200 baris atau > 5 method tidak berhubungan
Tim besar, jangka panjang Wajib SRP ketat Mencegah konflik & memudahkan maintenance bertahun-tahun
Aturan Emas Kalau Anda ragu apakah perlu memisahkan — coba tanya:

"Kalau bagian X berubah, apakah saya harus menyentuh bagian Y juga?"

Kalau ya, berarti class melanggar SRP. Pisahkan.

11. Latihan & Tugas

Latihan 1 — Identifikasi Tanggung Jawab

Perhatikan class berikut, lalu sebutkan berapa tanggung jawab di dalamnya:

class StudentManager
{
    public function validateStudent(array $data): bool { ... }
    public function calculateGPA(array $grades): float { ... }
    public function saveToDatabase(array $data): void { ... }
    public function generateTranscript(array $data): string { ... }
    public function sendEmailNotification(array $data): void { ... }
}

Target: Sebutkan 5 tanggung jawab + peminta perubahan untuk tiap tanggung jawab.

Latihan 2 — Refactor Kode

Ambil class StudentManager di atas, lalu pecah menjadi class-class yang masing-masing mengikuti SRP. Wajib menyertakan:

  • Minimal 5 class terpisah.
  • Gunakan interface untuk penyimpanan (misal StudentRepositoryInterface).
  • Gunakan abstract class untuk notifikasi (misal Notifier).
  • Tunjukkan polimorfisme dengan membuat 2 turunan notifikasi (email & SMS).
  • Buat class koordinator StudentService yang merangkai semuanya.

Latihan 3 — Analisis Sendiri

Buka salah satu project PHP Anda sebelumnya. Audit SRP dengan tabel:

ClassMethodTanggung JawabMelanggar SRP?
.........Ya/Tidak

Untuk setiap pelanggaran, tuliskan usulan perbaikannya.

Tugas Akhir — Refactor Project Sebelumnya

Ambil project Praktikum 2 atau Praktikum 3 yang sudah Anda buat, lalu terapkan SRP. Kumpulkan:

  1. Kode sebelum refactor (1 file besar).
  2. Kode sesudah refactor (banyak file kecil).
  3. Class diagram sebelum dan sesudah.
  4. Penjelasan tertulis (maksimal 1 halaman):
    • Tanggung jawab apa saja yang dipisahkan.
    • Class mana yang menggunakan interface.
    • Class mana yang menggunakan abstract class.
    • Di mana polimorfisme terlihat.
